# Test Management Standard

这份文档定义 `testing/` 体系里的“测试如何被管理”。

它回答的不是“某个场景怎么执行”，而是：

- 一个测试需求如何进入体系
- 应该归入 `smoke`、`regression` 还是 `feature`
- 谁来维护场景契约、夹具、证据和结论
- 什么结果可以作为 merge gate
- 新经验应该沉淀成什么，旧资产又该如何退役

如果你要看“怎么执行”，优先看 [testing/unified-testing-playbook.md](unified-testing-playbook.md)。
如果你要看“资产放哪里”，优先看 [testing/test-asset-management.md](test-asset-management.md)。

## 一、管理目标

测试管理的核心目标有 4 个：

1. 让联调、smoke、regression、E2E 都有统一入口，而不是靠个人记忆找脚本
2. 让每次测试都有明确的场景边界、准入条件、证据和结论
3. 让新增经验沉淀为“构造过程”，而不是散落的一次性结果
4. 让测试结论能支撑开发、排障、回归、合并决策，而不是制造噪音

## 二、文档分工

`testing/` 根下 4 份核心文档分工如下：

- `docs/rules/testing.md`
  - 根入口，说明目录和阅读路径
- `testing/test-management-standard.md`
  - 说明测试如何建账、执行、结项、晋升、清理
- `testing/unified-testing-playbook.md`
  - 说明测试如何准备环境、拉起运行时、分层执行、判定结果
- `testing/test-asset-management.md`
  - 说明场景、夹具、runner、证据等资产如何分类与治理

如果一个问题属于“怎么测”，看 playbook。
如果一个问题属于“怎么管”，看本文件。

## 三、命名要求

测试资产命名必须优先表达“测什么”，而不是只表达“看起来像什么”。

至少要说清楚以下信息中的大部分：

- 测试层级，例如 integration / e2e / harness
- 目标对象，例如 metadata 生成接口、high-code 数据 API、低开全链路
- 核心边界，例如 login、CRUD、query-conditions、permission-boundary

应避免以下低信息密度命名：

- `database-regression`
- `feature-test`
- `smoke-check`

更好的方向是：

- `metadata-and-high-code-data-api-regression`
- `lowcode-full-app-lifecycle`
- `auth-ldap-login`

如果一个名字无法让没有上下文的人快速判断“它到底测什么”，那这个名字就还不够好。

## 四、统一入口规则

联调、harness、smoke、regression、E2E 相关任务，统一按以下顺序进入：

1. 先看 `docs/rules/testing.md`
2. 再看本文件，确认这次测试属于哪类任务、是否已有正式场景
3. 再看 `testing/unified-testing-playbook.md`
4. 最后进入目标场景的 `testing/integration/**` 或 `testing/e2e/**`

禁止以下做法直接充当第一入口：

- 零散聊天记录
- 临时 shell 历史
- 某次运行生成的 report
- `docs/articles/` 中的历史经验文章

这些材料可以辅助理解，但不能替代正式入口。

## 五、测试请求如何分类

每个测试请求都必须先分类，再决定执行方式。

### 1. `integration/smoke`

适用于：

- 验证主链路是否可用
- 验证服务接入是否通
- 验证平台关键入口是否还能打开并完成基础动作

特点：

- 覆盖窄
- 稳定性要求高
- 适合作为日常守门

### 2. `integration/regression`

适用于：

- 重大重构合并前验证
- 兼容性回归
- 涉及跨模块、跨运行时、跨数据模型的风险改动

特点：

- 覆盖深
- 允许包含较重夹具和较长执行时间
- 需要明确排除项、上下文要求和证据口径

### 3. `integration/feature`

适用于：

- 新功能联调
- 口头指定用例
- 尚未稳定、仍在探索边界的场景

特点：

- 默认先走 harness
- 重点是澄清用例和沉淀经验
- 稳定后要考虑晋升到 `smoke` 或 `regression`

### 4. `e2e`

适用于：

- 已具备稳定自动化条件的场景
- 能自动拉起前后端和必要依赖
- 能稳定生成报告并重复运行

注意：

- `e2e` 是执行形态，不是替代场景契约
- 所有 E2E 都应回指对应的集成场景契约和用例表

## 六、一个测试需求如何进入体系

标准流程如下：

1. 判断是否已有对应场景
2. 如果没有，在 `testing/integration/**` 下新建场景
3. 补齐 `scenario.yaml`、`contract.md`、`cases.md`
4. 如果需要 AI agent / 人工辅助，再补 `harness.playbook.md`
5. 如果已满足稳定自动化条件，再补 `testing/e2e/**` manifest
6. 如果新增了共享依赖，再抽象出公共 fixture 或 runner

新增场景前必须先回答 3 个问题：

- 这个场景验证的主目标是什么
- 它依赖哪些 runtime / frontend / service / identity / data fixture
- 它的通过标准和排除项是什么

如果这些问题还回答不清，就不应直接进入正式场景目录。

新增测试用例还必须完成卫生准入：

- 组件级用例必须归属到具体模块和组件，并说明覆盖的公开行为结果或领域规则
- 系统集成级用例必须归属到正式场景和稳定 case ID，并在 `cases.md` 中记录所属分支和可观察结果
- 分支分类优先使用 `normal`、`invalid/error`、`empty/boundary`、`state/transition`、`permission`、`dependency/recovery`；确实不适用时写 `N/A`
- 禁止用读取源码后的字符串/正则匹配、代码结构/源码模式断言、纯覆盖率补数或无归属的一次性测试充当正式用例

## 七、角色与责任

这里的责任是“角色责任”，不要求必须由固定岗位承担，但每轮执行都必须有人对这些角色负责。

### 1. 场景责任人

负责：

- 维护场景契约和用例表
- 明确通过标准、排除项、上下文依赖
- 决定场景是否仍应保留在 `feature`，还是晋升为 `smoke/regression`

### 2. 夹具责任人

负责：

- 维护共享 fixture 的输入输出边界
- 维护 lifecycle 与 preflight 语义
- 保证夹具不是私有临时脚本的堆积

### 3. 执行责任人

负责：

- 按场景契约和 playbook 执行测试
- 保留完整证据
- 区分“产品回归”“执行前提缺失”“运行时基线失真”

### 4. 结论责任人

负责：

- 审核测试结论是否与证据一致
- 审核排除项是否合理
- 判断是否具备合并条件或是否需要继续补测

同一人可以兼任多个角色，但责任不能缺位。

## 八、准入与退出标准

### 场景准入

一个场景要进入正式体系，至少必须具备：

- 明确的场景目标
- 明确的 fixture 依赖
- 明确的通过标准
- 可追溯的 case ID

### 执行准入

一轮正式执行开始前，至少要满足：

- 目标场景契约存在
- fixture 预检可执行
- 目标 runtime / frontend / data / identity 来源可解释
- 需要的组织、权限、账号、公司上下文已补齐或明确标记缺失

如果执行前提不满足，应先记为“前提缺口”，而不是直接打业务回归结论。

### 场景退出

一个场景在以下情况下可以降级、迁移或退役：

- 已被更稳定的新场景替代
- 其能力已完全被更上层正式场景覆盖
- 依赖的产品能力已下线
- 只剩历史参考价值，不再适合作为当前守门场景

退役前应先补引用或迁移说明，不能直接硬删入口。

## 九、执行批次如何管理

每一轮正式执行都应有最小的 run 语义：

- 对应的场景 ID
- 对应的 run ID 或日期标签
- 本轮执行的范围
- 本轮排除项
- 本轮使用的 runtime / app-root / frontend / identity / fixture 版本或来源

同一个场景可以有多轮 run，但不能把旧 run 的结果混进新 run 的总结里。

如果是重大重构回归，还应额外记录：

- 对应 `dev` 基线
- 当前分支 HEAD
- 已同步的 `dev` 提交及同步方式；功能/修复通过 MR 合入并保留逻辑提交，禁止改写共享历史，不能把 rebase 当作所有分支的前提
- 是否使用 freshly-built 产物，还是借用 runtime

## 十、结果分类规则

每条 case 结论至少应落入以下几类之一：

- `pass`
- `fail`
- `blocked`
- `excluded`
- `precondition-gap`
- `runtime-baseline-invalid`
- `test-command-invalid`（命令或 reactor 错误，目标测试尚未实际执行）

判定原则：

- `fail` 只用于有足够证据支持的真实产品问题
- `blocked` 用于依赖未就绪、服务未通、关键前提阻断
- `precondition-gap` 用于账号、组织、公司、权限等上下文未补齐
- `runtime-baseline-invalid` 用于运行时本身已失真，当前 run 不适合作为 merge gate
- `excluded` 必须记录原因，且默认视为临时状态而不是永久规则

不要把所有异常都归到 `fail`，否则报告会污染，结论也会失真。

## 十一、什么结果可以作为 merge gate

要作为 merge gate，至少要满足：

- 运行时来源可信
- fixture 预检通过
- 排除项已显式记录
- 结果与当前场景 case universe 一致
- 报告没有把旧 run 的结果混入当前 run

以下结果不能直接作为 merge blocker：

- 借用 runtime 且基线已失真
- 缺少公司、组织、权限上下文
- HTML 登录页或代理误路由被误认成业务接口失败
- 场景外的已知项目自身问题被错误纳入范围

## 十二、证据与报告闭环

每一轮执行都必须先有证据，再有结论。正式 runner 的既有输出位置可以保留；需要长期追溯的证据须在清理前保存到任务或 CI 制品。

最低要求：

- 证据落到 `tmp/testing-evidence/**`
- 报告引用场景 ID 和 case ID
- 报告明确记录排除项、前提缺口和阻断项
- 关键失败要能回溯到原始日志、响应、trace 或截图

证据的用途是支撑判断，不是替代标准文档。

## 十三、缺陷闭环规则

发现问题后，至少要继续回答 3 个问题：

1. 这是产品缺陷、环境问题，还是测试体系自身缺口
2. 这个问题应该修代码、补夹具、改契约，还是改报告口径
3. 这个经验应该沉淀为场景规则、公共 runner 能力，还是仅作为一次性现场记录

只有当“为什么会错、以后如何避免”也被回答清楚时，这次测试才算真正完成闭环。

## 十四、场景晋升规则

场景演进建议遵循：

1. 新需求先进入 `integration/feature`
2. 稳定后晋升到 `integration/smoke` 或 `integration/regression`
3. 满足自动化条件后，再补 `e2e` manifest

晋升前至少要确认：

- 用例不再频繁变化
- 夹具依赖清晰
- 通过标准稳定
- 报告口径稳定

如果这些条件还不成立，就应继续保留在 harness 主导的 `feature` 场景中。

## 十五、经验沉淀规则

每完成一轮重要执行，都要问：

- 新学到的是“构造过程”还是“构造结果”

只有以下内容应进入长期标准：

- 新的场景边界
- 新的 fixture 预检规则
- 新的结果分类规则
- 新的执行顺序或判定标准

以下内容原则上不应直接进入长期标准：

- 某次具体 run 的临时报错文本
- 某次临时数据样本
- 某次本地目录路径
- 某次执行生成的 inventory / summary

## 十六、审查与清理节奏

建议按以下节奏管理：

- 每次新增正式场景时，检查是否与已有场景重复
- 每次引入新 fixture 时，检查是否已有共享实现
- 每次完成重大回归后，复盘哪些经验应进入标准文档
- 每次测试跑完后，及时清理无用后台进程，只保留最新且必要的进程
- 每个阶段性里程碑后，清理失效桥接、重复文章和过期夹具

对后台进程再补一条硬规则：

- 默认杀掉本轮自己拉起的进程；如果要保留，必须在报告或交接说明里写明 `PID / 端口 / 用途 / 预计保留时长`

清理顺序应始终是：

1. 先建立新正式入口
2. 再把旧入口降级为引用或桥接
3. 最后删除完全失效资产

## 十七、AI Agent 使用规则

AI agent 参与联调、回归、smoke、E2E 时，默认遵循：

1. 先从 `docs/rules/testing.md` 进入
2. 先确认这是管理问题、执行问题还是资产治理问题
3. 再读取对应根文档和目标场景
4. 新经验优先沉淀为规则、夹具、runner 或场景契约，不要只留下聊天结论

这样做的目标不是增加流程，而是降低“每次都从头摸索”的成本。
