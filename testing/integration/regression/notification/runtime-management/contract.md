# 通知运行时配置管理验收合同

本场景验证应用部署后管理已有通知模板及渠道参数的完整闭环。模板名称及载荷契约只读；数据库独有历史模板只读。模板通过原 Provider 的数据库高优先级完整覆盖，渠道参数通过原统一配置管理；两者撤销后删除覆盖，随后跟随部署默认。其他组件保留原恢复规则。

## 验收层级

组件、数据库及 Controller 组合验证见 [cases.md](cases.md)。完整应用验收使用当前 worktree 构建的 Mothership 和主应用、独立 MySQL 8.3、共享 Redis 7、文件默认定义及真实用户名密码认证。页面不得拦截或伪造产品 API。测试资源仅绑定回环地址，账号、密钥和运行目录均在忽略的 tmp 下。

| Case ID | 成功标准 |
| --- | --- |
| NRM-SHELL-001 | 真实登录后从系统菜单进入列表、查看、编辑和渠道目录；纯检查不写入；保存完整覆盖，停用及只读契约保持正确，审计身份为真实操作人 |
| NRM-SECRET-001 | 正式渠道凭据策略装配后可替换凭据，管理响应不含真实值，并能显示配置状态 |
| NRM-RBAC-001 | 匿名及未授权 API 被拒绝；无权限菜单隐藏；直接访问四个通知管理页面显示拒绝说明，既不初始化数据请求，也不显示编辑控件；模板权限不能代替配置权限 |
| NRM-UPGRADE-001 | 旧表结构样本由正式模型生命周期升级，补齐名称键、版本及唯一约束；重启后覆盖保持，历史独有模板仍只读 |
| NRM-CLUSTER-001 | 两个独立 Mothership JVM 连接同一隔离数据库和 Redis，预热后跨节点读取保存和撤销的新状态；不以两次同节点请求代替多实例 |
| NRM-DEFAULT-001 | 部署 V2 默认后原覆盖保持，标示默认变化；拒绝 V1 页面版本写入；撤销后跟随 V2 |
| NRM-DEFAULT-002 | 撤销后再部署 V3，模板和渠道参数继续跟随 V3，数据库无对应覆盖 |

## 运行与证据

操作步骤见 [harness.playbook.md](harness.playbook.md)。完整应用断言由主应用测试目录中的 `full-app-acceptance.cjs` 执行；页面使用真实产品 schema，API 使用真实认证身份。跨实例采用每节点独立登录，无共享 HTTP 会话承诺。

证据保存到 `tmp/testing-evidence/notification-runtime-management/`，包括源码基线、构建日志、启动日志、各阶段断言、迁移前后结构和页面截图。不得保存明文密码、Token 或渠道凭据。结果只覆盖该次构建与列明环境。

实际供应商外发送达由用户明确排除，不作为本次验收条件。不连接生产、不迁移真实生产历史数据、不执行发布。全仓既有失败按实施验收记录单列，不能以本场景通过宣称全仓门禁全绿。
