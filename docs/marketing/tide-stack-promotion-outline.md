# 潮汐栈宣传资料大纲

> 内容大纲。基座能力与接入范围对应手册；超出现有交付的内容按展望介绍。

**目标读者**：企业管理者、数字化建设负责人、IT 架构师、业务产品负责人、开发者、实施与运维团队。

**主定位**：为模型驱动与 AI 辅助开发提供统一的企业级应用基座。潮汐栈以业务模型承载属性、关系、动作、事件、视图和访问权限，由前后端基座共同提供页面、接口、业务执行、数据治理与系统集成能力。团队可以选择 AI 辅助开发、IDE 专业开发或可视化构建，复用同一套模型契约、插件机制与运行能力。

**建议主线**：先展示应用基座如何承接页面、业务执行、权限、集成和部署等公共工作，再说明业务模型如何把业务定义落实为应用。以插件机制支持企业专有能力，以容器化交付和 Docker / Kubernetes 开发运行后端适配环境，让读者同时看清能力覆盖、开发入口和实际部署条件。

**基座总览图**：[企业级应用基座架构（独立 SVG）](../handbook/docs/concepts/architecture/.assets/tidestack-foundation-architecture.svg)，用于说明多种开发方式与前后端公共能力的关系；配套[基座介绍与能力对照](tidestack-foundation-architecture.md)可单独使用。

**模型主线图**：三环 + 一个圆心。圆心是“业务模型（本体）”，即已沉淀的业务语义资产；内环是业务与治理要素（属性、关系、动作、事件、视图、访问权限），中环是承担专门职责的模型（数据、UI、UI Schema、WebAPI、逻辑流、审批流、菜单、权限、RPC），通过投影、引用、调用和实现与业务语义衔接，外环是业务开发流程闭环（需求 → 建模 → 构建 → 验证 → 发布 → 运行 → 反馈 → 需求）。外环的“建模”是语义和治理要求进入圆心的入口。

**编辑口径**：对外正文使用“潮汐栈（TideStack）”；“模型”“元数据”“投影”“插件机制”与手册保持一致。业务模型区分投影、引用、调用和实现；业务动作与事件按已有运行时契约介绍，具体插件和渠道按模块装配与配置条件说明。业务模型可表述为本体化智能的语义基础，不直接宣称已经提供完整的本体编辑、知识图谱存储或语义推理引擎。

## 一、企业信息系统建设的挑战与机遇

### 1.1 系统开发：从重复交付走向可复用建设

**内容梗概：** 企业需求变化快，系统建设却常依赖定制编码和点对点集成。不同系统重复定义数据、流程和权限，使交付、协同和后续改造成本不断累积。介绍模型化和组件化建设如何把可复用的业务知识沉淀下来，让团队把精力更多投入差异化业务。

### 1.2 系统智能化：从接入大模型走向理解业务

**内容梗概：** 大模型降低了自然语言交互、内容处理和任务辅助的门槛，但企业智能应用仍需要准确的业务语境、可靠的数据边界、权限约束和可执行的业务动作。由此引出结构化业务模型的价值：为 AI 理解企业对象、关系和规则提供更清晰的上下文。

### 1.3 面向未来的延续性：系统需要跟着业务演进

**内容梗概：** 系统的生命周期通常长于单次项目和技术选型。业务调整、团队交接、基础设施升级和新技术接入都要求系统能够理解、维护和扩展。强调让业务定义、功能实现与运行环境保持清晰边界，有助于把系统从一次性交付变成可持续演进的业务资产。

### 1.4 机遇：让业务语义贯穿建模、交付与运行

**内容梗概：** 将前三节收束到同一个问题：业务语义不能只停留在需求文档或少数人的经验中。用三环主线图说明，业务模型承载内环的业务与治理要素，中环将相应语义落实为专门职责模型并连接执行能力，外环把需求、建模、构建、验证、发布、运行和反馈组织成持续交付流程。重点讲清“建模”是语义进入系统的入口，运行反馈可以回到模型治理和后续建模中，形成可持续演进的资产。

**本章落点：** 企业需要在提高开发效率的同时，让业务定义保持清晰、系统具备扩展空间，并为智能化应用提供可理解、可执行的业务语义。

## 二、潮汐栈的核心优势

### 2.1 基于模型的声明式构建

**内容梗概：** 通过模型描述业务对象及其结构、关系、行为和访问边界，再将相应定义投影到数据、界面、接口、菜单和权限，并通过逻辑流、代码与审批流执行处理。说明模型如何减少重复定义，以及它如何成为协作、复用、审查和变更治理的共同依据。

**展开重点：** 用“业务意图 → 模型 → 多种运行能力”说明声明式构建；避免写成“完全不用写代码”，而是强调平台承接标准建设，专业开发承接明确的扩展边界。

### 2.2 业务开发与功能实现合理分层

**内容梗概：** 业务侧关注业务语义、模型组合和访问边界，平台侧提供数据、逻辑流、审批流、安全和运行时等通用能力。通过稳定的模型契约和扩展边界连接两者，使常见需求可以配置组合，复杂需求通过正式代码扩展、外部系统适配或独立界面实现。

**展开重点：** 说明专业开发不是低代码的兜底，而是在平台边界明确之后补充新能力；所有结果仍回到同一套模型、页面、接口、权限和发布机制。

### 2.3 业务模型即业务语义与治理边界的共同载体

**内容梗概：** 业务模型不是单一的数据表定义，而是组织业务概念及其访问边界、并关联多类平台模型的枢纽。说明同一组属性、关系、动作、事件、视图和访问权限如何连接数据、界面、API、逻辑流、菜单和审批流程，并为后续语义检索、知识关联及智能体调用提供一致的业务上下文和治理约束。

**展开重点：** 标准业务模型由六类要素构成：属性描述对象记录什么，关系描述对象关联什么，动作定义允许执行的业务操作，事件记录已发生的业务事实，视图组织查询、展示与维护，访问权限约束可用操作、记录范围与字段。事件订阅负责响应事件；业务模型及其投影定义共同落实运行时约束。

**与三环的关系：** 内环回答“业务对象如何定义和约束”，中环回答“系统如何实现”，外环回答“团队如何持续交付和演进”。模型主线图解释业务语义如何变成应用，基座总览图说明这些应用由哪些公共能力承载。

**表达边界：** 可以将业务模型介绍为通向本体化智能系统的基础；除非已有对应产品能力和案例，不应将其表述为已经内置完整的本体编辑、知识图谱推理或语义推理引擎。

### 2.4 微内核与全插件化

**内容梗概：** 以稳定的核心契约连接可扩展的功能模块，将插件化贯穿核心引擎、基础能力、应用界面和开发工具。突出统一运行时基座与开发平台本身也由模块装配形成，企业可以沿既有扩展点补充能力，并将定制成果封装为可复用组件。具体构造方式在第三章展开。

### 2.5 开放、融合与渐进式采用

**内容梗概：** 潮汐栈不要求企业一次性替换现有系统。企业可以从一个模型、一个应用或一个业务领域开始，逐步引入平台能力；标准组件可以通过扩展机制与既有高代码系统协同，也可按需采用独立组件。用开放标准、可组合边界和逐步迁移说明平台如何降低采用门槛。

**底层理念：** 用开放化、融合化和标准化支撑上述优势：开放化让组件和扩展点可以接入既有生态，融合化让低代码、专业代码和 AI 在同一模型契约上协作，标准化让业务意图、访问边界和运行约束具备共同表达方式。

**表达边界：** 对开源组件数量、扩展点数量和可独立采用的范围，按当前实际发布状态与集成方式核实后再写入宣传文案。

## 三、微内核与全插件化的构造架构

**本章定位：** 说明潮汐栈的基座和平台由什么构成、能力通过什么机制接入，以及定制能力如何持续演进。与下一章的部署架构并列，分别回答“系统如何组成与扩展”和“系统如何部署与运行”。

### 3.1 微内核：稳定核心契约，开放能力边界

**内容梗概：** 从微内核的设计思想介绍潮汐栈：在清晰的架构分层中保留稳定的核心契约和执行机制，将具体功能、技术适配和业务定制放到相应的扩展模块中。解释核心与扩展之间的职责边界，使符合已有扩展契约的新能力可以通过追加模块接入，减少对核心代码的改动。突出稳定核心与持续扩展并存的长期价值。

### 3.2 全插件化：贯穿引擎、能力、界面与开发平台

**内容梗概：** 将“全插件化”作为贯穿平台各层的构造方式展开，用具体扩展点说明覆盖范围，让读者看到平台的可扩展性落在哪里、能够解决什么问题。

| 扩展层面 | 代表性扩展 | 业务价值 |
| --- | --- | --- |
| 核心引擎与模型 | 字段类型、逻辑流节点、表达式与脚本能力 | 将专有业务语义和处理能力纳入模型与流程 |
| 基础能力与外部适配 | 通知渠道、消息中间件适配、外部审批引擎桥接 | 接入企业既有基础设施和业务系统 |
| 应用界面与交互 | 微前端、布局组件、平台组件库 | 复用专有交互能力，承载复杂页面与子系统 |
| 开发平台 | 开发模块、模型编辑界面、元数据检查器 | 让新增能力具备配套的配置、编辑和管理入口 |

### 3.3 基座与平台：基于共同模型契约的模块装配

**内容梗概：** 介绍统一运行时基座与开发平台两种产品形态如何由下层能力装配形成。两者围绕共同的模型契约协作，分别组织运行态和开发态的能力，使一项扩展既能进入应用运行，也能按需提供对应的开发管理支持。

| 产品形态 | 构造方式 | 主要职责 |
| --- | --- | --- |
| 统一运行时基座 | 组合核心引擎、能力运行时、应用元数据和环境适配模块 | 承载应用，加载已发布模型，由各能力运行时解释与执行 |
| 开发平台 | 组合公共能力、开发管理模块与开发辅助工具 | 提供模型编辑、元数据管理、版本治理等开发支持 |

**讲述重点：** 基座与平台的入口承担装配和承载职责，具体能力由相应模块提供。新增能力可分别交付运行时扩展与开发态模块，复用已有模型管理和生命周期机制。

**产品延伸：** 独立运维平台按规划介绍，发布前核实交付状态。已由开发平台和运行基座提供的实例管理、状态、日志与指标，应按现有手册分别说明。

### 3.4 插件机制：标准接入，组合复用

**内容梗概：** 用简明语言介绍扩展包如何进入平台：自动配置负责启动时装配，SPI 负责发现注册的扩展实现，模型元数据、模板和脚本由相应运行时读取和解释。后端扩展包、前端组件和开发模块各自通过正式入口接入，沿用平台的模型、权限与生命周期约定。强调企业定制能力可以封装、复用，并与平台核心保持清晰边界。

**建议示例：** 将企业专有计算规则封装为逻辑流节点，提供节点参数定义和执行实现，接入后即可在不同业务逻辑流中反复组合使用。通过这个例子展示“专业开发形成能力，模型配置复用能力”的关系；具体开发流程留到高低代码融合章节展开。

**配图：** 使用[基座总览图](../handbook/docs/concepts/architecture/.assets/tidestack-foundation-architecture.svg)的插件机制泳道说明模型、数据、流程、渠道与前端插件；具体注册、装配与生命周期参照手册的[插件装配图](../handbook/docs/concepts/architecture/.assets/plugin-and-module-assembly.svg)。

**与三环的关系：** 微内核和插件机制支撑内环要素、中环投影和外环开发流程持续扩展。插件化关注“能力如何组成”，三环关注“业务语义如何变成应用并持续交付”，两者互相支撑但不互相替代。

## 四、云原生与灵活部署架构

**本章定位：** 说明同一套业务模型和平台能力如何适应不同规模、可用性和运维条件。插件化关注能力组成，部署架构关注运行拓扑；插件与独立服务之间不要求一一对应。

### 4.1 容器化交付与开发运行后端

**内容梗概：** 仓库提供 Docker 镜像和 Docker Compose 安装材料，外置配置、应用元数据、扩展包与持久数据分别管理。开发平台通过 Docker 或 Kubernetes 运行后端管理测试应用和开发助手。Kubernetes 后端创建单副本 Deployment、Service 与可选 Ingress，通过共享工作区和 PVC 接入持久化。

| 部署对象 | 当前材料或机制 | 说明重点 |
| --- | --- | --- |
| 开发平台安装 | Docker 镜像、Docker Compose | 平台入口、数据库、消息队列、工作区与持久数据 |
| 测试应用与开发助手 | Docker / Kubernetes 运行后端 | 实例创建、启停、状态与日志；端口、域名及存储适配 |
| 平台及正式应用的 Kubernetes 部署 | 部署方自行编排 | 集群入口、工作区映射、依赖、凭据、探针与升级恢复 |
| 原生部署 | 自行准备 JVM 进程、静态服务与配置 | 服务启动、访问入口与持久化职责 |

### 4.2 按环境规划入口、存储与运行观测

**内容梗概：** Docker 可使用临时端口或 APISIX 稳定域名，Kubernetes 可使用 NodePort 或 Ingress。入口、TLS、共享工作区、PVC、数据库、消息服务与文件存储各自配置；开发平台的健康检查和指标采集，以及运行实例的状态和日志，提供环境验证的依据。

**表达边界：** Kubernetes 支持描述的是已实现的开发运行后端及可编排的部署方式。多副本高可用、自动伸缩、完整 Helm 安装包、无停机升级和微服务拆分需按实际交付方案另行验证，不能由“支持 Kubernetes”推导得出。部署拓扑与条件以[部署架构手册](../handbook/docs/operations/deployment-architecture.md)为准。

## 五、四大核心组件

**本章定位：** 把三环中的中环落成可理解的执行链。四大组件不是四个彼此孤立的功能，而是“一个业务模型源头 + 三条执行链”：业务模型组织业务语义，动态数据模型、逻辑流引擎和审批流引擎分别承载数据、机器逻辑和人员流程的运行。

**内容梗概：** 先展示业务模型投影数据、页面、接口与权限定义，再说明逻辑流、代码与审批流如何按各自契约执行。重点区分逻辑流与审批流：前者面向机器执行和即时返回，后者面向人员参与和跨时段流转。

### 5.1 动态数据模型

**内容梗概：** 运行时定义和管理数据结构，以统一的数据模型承载业务对象、字段、关系和查询语义，支持平台围绕模型提供数据访问与查询能力。重点说明它如何为业务模型及上层功能提供数据基础，以及模型变更、版本治理和既有代码接入的边界。

### 5.2 逻辑流引擎

**内容梗概：** 将功能点中的判断、数据处理、校验、分支和服务调用编排为可执行逻辑流，连接平台能力和业务逻辑。可通过节点扩展接入企业专有能力。与审批流区分：逻辑流处理机器执行和即时返回，审批流处理人员参与的长周期业务流程。

### 5.3 审批流引擎

**内容梗概：** 为需要人员参与、任务流转、参与人计算和结果追踪的业务流程提供建模与执行能力，并与组织架构、权限和消息通知协同。通过适配机制连接外部工作流引擎，便于与企业既有流程平台协同。

**表达边界：** 外部引擎的能力因适配器而异。介绍具体渠道时，应核对其支持的流程发起、任务查询、动作代理和结果同步范围。

### 5.4 业务模型

**内容梗概：** 以业务语义和治理边界为核心，组织数据、权限、逻辑流、UI、API、菜单和工作流等模型的定义与投影。它将前三项能力及平台服务组合为面向业务的可管理模型。

**展开重点：** 说明标准业务模型由属性、关系、动作、事件、视图和访问权限共同构成。属性与关系参与数据模型投影，视图参与 UI 模型和 UI Schema 投影，业务操作形成接口、行为及权限契约；逻辑流、代码、审批流与 RPC 等能力通过相应引用、调用或实现关系协作。投影范围与生效时机取决于模型配置和已装配能力。

### 建议配图

展示“业务模型（属性、关系、动作、事件、视图、访问权限）→ 数据模型、UI/API、逻辑流、权限、审批流 → 应用运行”的关系，帮助读者理解核心组件如何协作。

## 六、低代码、高低代码融合与 AI 开发支持

**本章定位：** 回答不同角色如何共同使用潮汐栈。业务开发者、实施人员、专业开发者和 AI 在同一份模型资产上协作，各自通过清晰的入口参与需求、建模、构建、验证、发布和运行。

### 6.1 可视化、配置化的低代码开发

**内容梗概：** 介绍通过开发平台管理业务模型、页面与表单、接口、流程、权限、通知、集成和版本的方式，以及低代码如何减少重复劳动、提升业务人员与开发人员的协同效率。用一个典型业务场景串起需求、建模、配置、验证、发布和运行。

**角色重点：** 业务开发者和实施人员负责业务语义与模型组合；专业开发者负责复杂逻辑、专有协议和新扩展能力；平台通过统一模型、权限和发布机制把不同产出合并到同一应用中。

### 6.2 高低代码融合

**内容梗概：** 说明标准业务采用模型和配置快速构建，复杂业务通过代码、扩展模块和外部系统集成补足。融合包括三种形态：代码融合（SPI 扩展点、逻辑流节点、数据模型插件、微前端和组件库）、工具链融合（Maven、IDE 插件和本地联合调试）、AI 融合（Skills 与 MCP）。

**统一性：** 自定义程序包可接入低代码基座，平台能力也可嵌入既有高代码应用；所有方式最终回到同一套页面、接口、权限、元数据和发布机制，不另建平行系统。

### 6.3 开发工具链协同

**内容梗概：** 介绍 Maven 插件、IDE 插件和本地平台联合调试等开发入口如何衔接建模、编码和调试，让低代码开发者与专业开发者在同一条交付链路中协作。

### 6.4 AI 辅助开发与人机分工

**内容梗概：** 介绍 TideStack Skills、MCP 和模型元数据规范如何为 AI Coding 工具提供项目及模型上下文，辅助理解模型、生成规范草稿、代码或测试。建议用“Find（定位）→ Explain（解释）→ Generate（生成）→ Review（校验与审核）→ Commit（提交沉淀）”说明 AI 如何参与开发流程。

**人机分工：** AI 负责理解、生成和重复性工作；人负责目标判断、例外处理、权限确认、审核和授权。AI 产出进入模型或代码资产前，应经过 Schema 校验、权限检查和版本治理。

**表达边界：** 按当前已交付的 AI 开发入口和示例描述可用能力，把计划中的自动化能力单独标注；模型接入本身不等于完整的 AI 应用生成能力。

### 6.5 可视化建模

**内容梗概：** 介绍当前可视化建模如何降低模型创建、理解和维护门槛，并说明它如何与元数据管理、版本治理、低代码开发和专业开发协作。区分“建模”这一外环流程环节与“可视化建模器”这一工具形态，具体支持范围按产品版本核实后写入。

## 七、基座能力与预置功能模块

**本章定位：** 回答“企业应用有哪些公共能力可以复用”。按[基座总览图](../handbook/docs/concepts/architecture/.assets/tidestack-foundation-architecture.svg)说明前端宿主、模型与执行、数据治理、企业服务、身份权限、公共运行、插件机制和环境适配，并以手册给出接入条件。

### 7.1 模型与数据基础

- 字段类型
- 数据字典
- 统一资源
- 多数据源支持

**讲述重点：** 从动态与类型化模型、关联查询、字段校验、唯一约束和引用检查，延伸到审计字段、逻辑删除、归档删除、历史版本、结构迁移与声明式初始化，说明数据全生命周期有哪些公共机制可以复用。

**可补充角度：** 字段类型不仅是存储类型，还可以承载校验、输入和展示语义；统一资源和数据字典让模型、组件和扩展进入统一的发现与装配边界。

### 7.2 运行时与集成基础

- 统一配置
- 统一缓存
- 消息队列
- 计划任务
- RPC 远程调用
- 前后端实时通讯
- 文件上传

**讲述重点：** 展示统一配置、缓存、任务调度、HTTP / RPC、消息队列和实时通信的协作。业务动作运行时负责契约校验、授权、事务与审计，业务事件提供事务后投递、持久化、失败重试和恢复，分别承接业务执行与后续协作。

**可补充角度：** RPC、消息队列、计划任务、缓存和实时通讯共同支撑同步调用、异步协作、定时执行和状态推送；每项能力都应说明当前支持的适配范围。

### 7.3 企业组织、安全与治理

- 组织架构
- 用户权限：功能权限、行级数据权限、列级数据权限
- 文档管理
- 业务日志
- 多语言

**讲述重点：** 说明企业应用如何使用组织和人员上下文控制访问、留存业务活动，并支持文档和多语言场景。权限粒度、审计范围和文档能力应配合实际产品界面或案例说明。

**重点表达：** 功能权限、行级数据权限和列级数据权限共同构成访问控制边界；组织架构是权限、审批流和通知的共同上下文。可用“同一用户在不同角色下看到什么”的对比场景解释权限价值。

### 7.4 用户体验与协同

- 个人门户
- 小组件
- 用户设置
- 多渠道消息通知，并支持扩展通知渠道
- 统计分析

**讲述重点：** 前端宿主提供微前端与布局生命周期、菜单与标签页、统一请求、实时订阅、多语言和主题；PrismUI、微组件、选择器、页面动作、公式与校验规则承接具体交互。个人化看板、用户设置、消息触达和统计分析共同组成日常工作体验。

**建议主链：** 统计数据集 → 报表视图 → 统计看板；个人看板通过小组件组合页面内容，通知模板、渠道和任务服务按业务定义衔接。避免把个人门户的具体聚合内容写成默认交付。

### 7.5 AI 与智能化扩展

- AI 大模型集成

**讲述重点：** 介绍模型调用、向量与知识检索、检索增强生成和外部 MCP 工具客户端接入，以及提供方配置与调用策略。运行时 AI 服务和用于开发的 Skills、模型规范及工具链分别说明。

**接口能力：** WebAPI 定义 HTTP 请求与响应契约，平台汇总动态接口文档并导出 OpenAPI 3.1；外部调用使用 RPC 契约和凭据配置，消息队列按绑定收发。MCP 当前指工具客户端接入，不能据此宣称全部平台能力已发布为 MCP 服务。

### 7.6 开放组件与开发者生态

- 动态数据模型
- 逻辑流模型
- PrismUI 声明式 UI 库
- 模型元数据规范
- TideStack Skills
- IntelliJ 与 VS Code 插件

**讲述重点：** 用代表性标准件说明开放生态如何支撑模型构建、界面开发和 AI 辅助开发；展示哪些组件已开源、可独立使用或可集成到现有系统，避免把“逐步开源”写成全部组件均已发布。

**与主线的关系：** 这些组件是模型、投影和开发流程的可复用标准件，不另建一套运行入口；扩展成果最终由平台的模型、菜单、权限和发布机制消费。

### 7.7 企业生态接入

| 渠道 | 已有接入范围 |
| --- | --- |
| 钉钉 | 企业登录、外部审批发起与结果接入、工作通知 |
| 飞书 | 企业登录、外部审批发起与结果接入 |
| 企业微信 | 企业登录、外部审批发起与结果接入 |
| 微信公众号 | 模板消息通知 |

**讲述重点：** 按渠道说明模块装配、企业凭据、连接、模板和回调配置。三种预置外部审批适配器采用结果接入模式，外部任务在厂商平台处理。飞书与企业微信通知、组织目录同步和应用入口发布按集成规划分别说明。

## 八、业务模型与本体论的未来延伸

**本章定位：** 说明统一应用基座和模型资产在本体化智能方向的延伸。前文说明业务模型如何进入应用和开发流程，本章说明它如何进一步成为本体化智能系统的语义来源；所有超出现有能力的内容都按展望口径表达。

### 8.1 从业务模型走向机器可读的业务语义

**内容梗概：** 以属性、关系、动作、事件、视图和访问权限为基础，将分散在表结构、流程、权限和接口中的业务语义与治理边界组织成更完整的模型体系。强调模型是人、AI 与运行时都能共同理解、约束和验证的标准件。

**展开重点：** 这层语义必须同时满足业务可评审、机器可消费、运行时可执行；业务模型是经过治理并与生产同步的语义来源，不是脱离系统的文档快照。

### 8.2 从统一模型走向本体化智能系统

**内容梗概：** 展望业务模型与本体、知识图谱、语义检索和智能体的结合。业务模型提供经过业务治理的语义来源；未来可进一步连接业务知识、数据和可执行动作，支持更准确的检索、推理与任务协作。

**智能化延伸：** 已有业务动作与事件运行时提供可执行契约和业务事实。未来可结合属性与关系开展语义检索和关联分析，结合视图提供面向任务的呈现，并让智能体在授权范围内调用业务动作、响应事件。现有动作与事件运行能力以手册中的契约为准，完整智能体编排和语义推理按展望介绍。

### 8.3 以治理与安全约束智能化

**内容梗概：** 智能系统需要遵循统一业务语义，也需要遵循身份权限、数据范围、流程规则和审计要求。强调业务模型与平台治理共同构成智能能力进入企业生产环境的基础。

### 收束表达

潮汐栈的长期方向，是让业务模型持续承载企业知识，并在系统构建、运行和智能化过程中发挥共同语义基础的作用。三环的运行反馈回到模型治理和后续建模，持续完善语义资产；这表达的是可治理的演进路径，不是未经验证的自动学习承诺。

## 编辑前的事实核对清单

- **主线图**：确认三环 + 圆心的图示口径：业务模型（本体）为圆心，内环为属性、关系、动作、事件、视图、访问权限，中环为以投影、引用、调用和实现连接的专门职责模型，外环为业务开发流程闭环；“建模”是语义进入圆心的流程入口。
- **术语**：统一使用“模型、元数据、投影、插件机制、融合开发”；不要用“自动生成、投射、二开”等模糊或不统一的表达替代。
- **核心优势**：用具体模型和业务场景说明声明式构建、业务与实现分层、微内核与全插件化、高低代码与 AI 融合，以及业务模型与本体的关联，突出各项机制带来的实际价值。
- **构造架构**：以稳定核心契约、模块装配和跨层扩展点支撑“微内核、全插件化”的表述。逐项核实扩展范围与依赖要求，区分启动期装配和模型运行时刷新，不将插件化泛化为任意模块均可热插拔、独立隔离或无停机升级。
- **产品生命周期**：开发平台和统一运行时基座描述为当前产品形态；运维平台需重新核实当前交付与官网状态，未核实前只按演进方向介绍。
- **部署架构**：区分开发平台、测试应用、开发助手和正式应用；以已有镜像、Compose 和 Docker / Kubernetes 运行后端说明现状。高可用、自动伸缩和服务拆分按实际交付方案核实。
- **可视化建模**：按开发平台当前能力介绍，核实具体建模范围、适用角色和版本差异，不再默认写成下一步规划。
- **AI 开发**：核实 Skills、MCP、IDE 插件、模型元数据规范的可用状态和真实案例，区分辅助生成与端到端自动交付。
- **开放生态**：确认各组件开源、可独立使用和可集成的状态。历史官网材料曾同时出现“核心组件全面开源”和“正在逐一开源”；发布前需以可访问仓库、版本和许可证统一口径。
- **外部审批引擎**：按适配器确认外部流程集成能力，不笼统承诺所有外部流程均可完整托管。
- **本体论**：明确当前业务模型能力与未来本体、知识图谱或推理能力的边界。
- **基座清单**：确认每项能力的产品名称、当前状态、适用版本和可公开示例。
- **网站内容状态**：发布前逐页确认“特性”“架构”“路线图”的正文与本大纲对应，不能把历史页面观察当成当前现状。
