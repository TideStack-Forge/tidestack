# 设计评审

跨模块边界、共享机制、正式扩展点或重要取舍变化时，评审需要同时面对当前设计、直接源码/配置、已确认需求和拟议差异。局部维护使用同样的证据原则，篇幅按实际复杂度裁剪。

## 评审与决定

1. 明确问题、范围、受影响对象和当前权威正文，区分代码事实、业务预期与提案。
2. 对关键意见分别记录采纳、暂缓、拒绝或需补证据及理由；未采纳方向不写成当前规则。
3. 已采纳结论回写原功能/需求/设计；重要决定按全仓唯一编号新增 ADR，保留背景和替代关系。
4. 同步父索引、模块入口、合同和术语；实现未落地或未验证时保留差距，不用 Accepted 推定完成。
5. 评审原文、单次日志与未决讨论保存到关联任务/PR/Issue；需要持续处理的风险和债务回写各自台账。

## 收口条件

读者能从当前正文理解采纳的机制和边界，从任务证据核对原始意见与处置；默认阅读链指向当前正文。未决问题有去向和所缺证据，不在备注中消失。规则及替代入口由[文档治理](documentation.md)统一维护，不再单独复制演进/维护工作流。
