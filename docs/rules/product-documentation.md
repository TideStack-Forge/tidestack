# 潮汐栈文档、宣传与推广口径规范

本规则约定长期文档的受众分层、平台定位和宣传边界；具体功能成熟度以当前模块设计、规格和验证证据为准。

同时，围绕“平台内容应该如何分层表达”，又提出了一套六层模型：

| 层级 | 名称 | 面向对象 | 核心作用 |
| --- | --- | --- | --- |
| 最高层 | 战略愿景层 | 决策者 | 阐述平台的长期目标和价值主张 |
| 第二层 | 价值定位层 | 中高层管理者 | 明确平台为不同角色带来的核心价值 |
| 第三层 | 设计理念层 | 管理者、架构师、技术负责人 | 解释平台的设计哲学、核心原则和底层逻辑 |
| 第四层 | 功能架构层 | 技术总监、架构师、实施负责人 | 说明平台的功能模块与架构设计 |
| 第五层 | 应用实践层 | 业务人员、实施人员 | 展示平台在具体场景中的使用方式和效果 |
| 第六层 | 技术实现层 | 开发人员 | 深入讲解平台的技术实现细节 |

这篇文章的目标，不是重新设计一套大而全的信息架构，而是给当前平台的文档、宣传和推广内容提供一套更稳定的表达口径。

## 一、当前仍然值得保留的平台主张

结合早期设计说明书与当前平台能力，可以把潮汐栈最值得长期坚持的平台主张总结为以下几条。

### 1. 不只追求“初版开发快”，而是追求全生命周期效率

这是最值得保留的一条。

很多低代码平台强调“很快能把第一版做出来”，但企业项目真正持续消耗成本的，往往是：

- 需求反复变化
- 验收前后的多轮调整
- 上线后的维护与扩展
- 与其他系统的持续对接

因此，潮汐栈的口径不能只停留在“快速搭建”，而应强调：

- 在需求持续变化下仍能维持较高交付效率
- 尽量把反复变更的成本留在模型和配置层解决
- 让开发、交付、维护和运营形成同一条连续链路

### 2. 低代码与 Pro Code 要能接力，而不是二选一

这也是平台区别于很多封闭式低代码产品的核心表达。

平台应始终强调：

- 能用低代码完成的部分，优先用低代码完成
- 超出平台舒适区的部分，允许通过前后端扩展点承接
- 代码扩展完成后，业务开发人员最好仍能继续在平台内接手配置和交付

这不是“低代码失败了才写代码”，而是“低代码先完成标准部分，代码继续承接复杂部分”。

### 3. 平台不能是孤岛，必须具备对接能力

企业应用天然会处在多系统环境中。一个不能顺畅对接外部系统的平台，即使单体内部效率再高，也很难持续创造真实价值。

因此，潮汐栈对外表达时应持续强调：

- 接口能力
- 消息能力
- 实时能力
- 外部系统集成能力
- 平台对不同对接方式的承接能力

### 4. 平台要兼顾从本地试用到统一运维的多种组织形态

平台的部署视角不应只面向一种规模。

从早期设计说明书到当前实践，潮汐栈都需要兼顾至少三种典型场景：

1. 团队成员各自在本地启动平台，分别开发不同项目
2. 团队在共享平台上协作开发多个项目
3. 企业 IT 团队把平台作为统一应用底座来管理一组系统

因此，平台口径里应同时包含：

- 开箱即用
- 团队协作
- 平台级治理
- 统一运维

### 5. 尽量贴近通用技术和工程实践，降低学习阻力

平台不应把价值建立在“必须先学习一整套专有知识”上。

更有说服力的表达是：

- 尽量贴近通用技术和行业规范
- 尽量让开发者沿用已有工程经验
- 把专有部分收敛到必要的模型抽象和扩展协议中

### 6. 版本治理和可持续交付是平台能力的一部分

版本控制、持续交付、升级回滚、长期维护，不应被放在“附加能力”里，而应被当作平台可信度的一部分来表达。

## 二、六层模型怎么用更合适

这套六层模型很有价值，但更适合作为“内容表达框架”，而不是直接替换 handbook 的一级目录。

原因很简单：

- 六层模型强调的是认知层次和受众层次
- 当前 handbook 更强调学习路径和操作路径
- 如果直接把 handbook 改成六层式导航，实际使用者反而更难找内容

因此，更合适的做法是：

- 把六层模型作为内容策划与口径校准框架
- 把当前 handbook 继续保持为角色与实践导向的阅读结构

## 三、推荐的映射关系

### 战略愿景层

适合承载内容：

- 平台长期目标
- 为什么要做这类平台
- 平台希望解决什么长期问题

推荐落位：

- `docs/handbook/docs/overview.md`
- 对外 PPT / 方案介绍开篇
- 官网或宣传页首页首屏与平台介绍区

### 价值定位层

适合承载内容：

- 不同角色为什么需要这个平台
- 对管理层、业务人员、技术人员分别带来什么价值

推荐落位：

- `docs/handbook/docs/overview.md`
- 方案汇报中的“角色价值”页
- 销售、实施、布道材料中的“适合谁”部分

### 设计理念层

适合承载内容：

- 为什么强调全生命周期效率
- 为什么强调低代码与 Pro Code 接力
- 为什么强调对接能力、可运维性和通用工程实践

推荐落位：

- `docs/handbook/docs/overview.md`
- `docs/handbook/docs/low-code/overview.md`
- `docs/handbook/docs/fusion-development/overview.md`

### 功能架构层

适合承载内容：

- 平台分成哪些能力模块
- 这些模块之间如何协同
- 为什么当前部署架构、功能架构是这样设计的

推荐落位：

- `docs/handbook/docs/operations/deployment-architecture.md`
- `docs/handbook/docs/reference/platform-capability-map.md`
- 架构介绍型对外材料

### 应用实践层

适合承载内容：

- 平台怎么被真正用起来
- 不同场景下怎么落地
- 通过什么路径完成应用交付

推荐落位：

- `docs/handbook/docs/getting-started/`
- `docs/handbook/docs/low-code/`
- `docs/handbook/docs/fusion-development/`
- `docs/handbook/docs/operations/`

### 技术实现层

适合承载内容：

- 核心概念
- 扩展点
- API / SDK / DSL
- 深度设计文档

推荐落位：

- `docs/handbook/docs/concepts/`
- `docs/handbook/docs/reference/`
- `docs/design/`
- `docs/rules/`（长期表达规则）或 `docs/marketing/`（宣传材料）

## 四、对当前 handbook 的使用建议

结论是：不建议因为这套六层模型而大改当前 handbook 结构。

更合适的方式是：

1. 保持当前 `快速上手 / 低代码开发 / 融合开发 / 运维管理 / 参考资料` 的主结构
2. 在这些入口页里补充更清晰的平台定位、设计哲学和角色价值表达
3. 把六层模型、平台主张和表达口径，沉淀到 `docs/rules/`（长期表达规则）或 `docs/marketing/`（宣传材料） 中，作为后续文档、宣传和推广内容的指导材料

这样做的好处是：

- 不打断当前手册的使用路径
- 不推翻已经形成的角色导向结构
- 仍然能逐步提升平台对外表达的一致性

## 五、建议长期统一的核心口径

后续无论文档、宣讲、方案汇报还是宣传材料，都建议尽量围绕以下几条统一表达：

### 平台是什么

潮汐栈是一款面向专业团队的低代码平台，强调低代码、专业开发和长期运维能力的协同，而不是单纯追求“替代开发”。

### 平台解决什么问题

潮汐栈重点解决的是企业项目中最常见的几类割裂：

- 原型与长期交付割裂
- 业务开发与专业开发割裂
- 开发交付与后续运维割裂

### 平台为什么有价值

潮汐栈的价值不只在于把第一版做快，更在于：

- 在需求持续变化下维持交付效率
- 用扩展机制承接复杂场景
- 用统一交付与维护方式支撑长期演进

### 平台与其他低代码产品的区别

更适合强调：

- 全生命周期效率
- 低代码与 Pro Code 接力
- 对接能力与平台开放性
- 版本治理与持续运维能力

而不建议过度强调：

- “零代码包打天下”
- “完全不需要开发”
- “所有场景都能只靠平台配置完成”

## 六、后续内容建设建议

如果要继续完善这套口径，建议优先做三件事：

1. 继续在 handbook 各主入口页补足“这一栏为什么存在”的解释
2. 把对外高频表达收敛成一套更短的标准话术，用于首页、方案汇报和宣传材料
3. 在 `docs/rules/`（长期表达规则）或 `docs/marketing/`（宣传材料） 里持续沉淀这类“平台表达层”的方法论，而不把它们全部塞进操作手册正文

## 总结

早期设计说明书今天最有价值的部分，不是具体架构草图，而是它对平台价值边界的判断：

- 平台价值应覆盖项目全生命周期
- 平台必须允许低代码与代码扩展接力
- 平台必须具备对接、运维和持续交付能力
- 平台需要兼顾个人、团队和企业级组织形态

六层模型用于组织受众和内容层次。

二者结合起来，最适合形成的不是一套全新目录，而是一套长期稳定的内容策划与对外口径方法。
