# 版本管理规范

## 工作流

采用以 dev 为集成主线、MR保留逻辑提交、独立发布ref交付的定制工作流。该模型沿用现有Jenkins发布分支/tag机制，允许后端、前端、SDK、IDE和插件独立交付；不另建一套Gitflow长期分支。

功能/修复从已确认的 dev 基线创建，MR合入 dev。默认保留可独立理解的逻辑提交，不做整体squash；合并前整理仅限本任务尚未共享的历史。禁止改写共享分支历史与已发布标签。仓库管理端的保护配置未在本地验证，本文件定义协作规则，不宣称服务器已强制启用。

## 分支、集成与生命周期

| 用途 | 命名、创建基线与目标 | 保护与回收 |
| --- | --- | --- |
| 主集成 | dev；功能与修复MR的集成目标 | 禁止共享历史改写；按变更范围完成验证再合入 |
| 功能/修复/重构 | feature/*、fix/*、refactor/*；从目标dev提交创建 | MR说明范围、接口影响、验证、原因；集成确认后回收任务分支和worktree |
| 后端快照/发版准备 | snapshot/v版本、release/v版本；从待交付提交建立 | 用途是触发已有发布链，不替代开发主线；来源与产物关联后保留必要发布追踪 |
| 前端交付 | frontend-web/snapshot/v版本、frontend-web/release/v版本 | 独立Web版本，触发规则见 [CI/CD](ci-cd.md) |
| 紧急修复 | hotfix/*；从受影响已发布提交/维护线创建 | 分支本身不触发后端发布，以hotfix标签交付；适用修复回流产品线 |
| 长期/客户维护 | 已有lts/v1、lts/boot27、ciecc等分支保持既有名称；新任务先确认具体基线与上游 | 按需维护、不承诺固定期限；不得凭分支存在宣称仍受支持 |

额外worktree默认放 .worktrees/；每次操作明确工作区，资源与集成见[并行协作](parallel-work.md)。本地当前主线是dev，旧develop示例不再作为检出依据；操作前核对实际远端引用，不在脏工作区盲目pull/切换。

## 多版本与客户维护

每次维护任务在关联Issue/MR记录目标维护线、起始提交、对应产品基线、交付对象及实际负责的任务。只有明确需求才启用该维护任务；没有固定支持期限，也不把旧分支自动宣布停止支持。

通用修复先进入适用产品线，再按兼容性移植到受影响维护线，保留原修复SHA与目标SHA并执行该线回归。紧急修复先落维护线时，跟踪向产品线回流。客户专属改动留在定制线；能由配置或正式扩展承载的差异不默认再开维护分支。

交付记录关联客户/版本线标识、实际提交、所用标签和产物digest；沿用已有明确标签，不杜撰客户标签格式或法律支持承诺。停止维护或交接时记录最后可恢复提交/标签、未决事项和接收方。

## 提交组织

一个提交表达一项可独立理解的逻辑意图；代码、行为测试和必要文档属于同一变更。分批提交在MR说明依赖顺序和可用基线，保留原因、关键取舍与任务关联。

标题使用 type(scope): 具体变化，scope可选。feat为新功能，fix为缺陷，refactor为保持行为的重构，test为测试，docs为文档，chore为工程维护；构建/流水线可用build/ci，性能改进可用perf。保留逻辑提交不等于保留无意义的临时纠错提交。

## 版本与标签

后端平台统一版本取根POM，依赖集中在BOM。正式使用X.Y.Z，先行版本使用alpha/beta/rc及必要序号，内部构建追加-SNAPSHOT。当前源码版本见[根POM](../../pom.xml)，无需在流程示例中维护第二个“当前版本”。

Maven插件、Web/SDK、IDE、Schema独立版本取其配置。[CI/CD](ci-cd.md)维护触发ref、版本推导与交付范围。发布标签对应明确提交，已共享标签保持指向；错误交付通过新版本及纠正记录处理。多仓组合交付列出每仓SHA、版本和产物，不能仅写“已同步”。

发布前按既有 [发布Skill](../../.agents/skills/publish-ouroboros/SKILL.md)及正式脚本执行；本地通过不等于发布成功。共享分支的实际保护设置和当前各维护线支持任务由远端平台/任务证据确认。
