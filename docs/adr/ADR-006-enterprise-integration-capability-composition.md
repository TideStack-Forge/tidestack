# ADR-006：企业集成按既有领域能力组合，组织关联独立于登录绑定

决定状态：Accepted，2026-11-15；第 5 项中的首页混合对象列表选择已由 [ADR-007](ADR-007-integration-management-workspace.md) 替代，其余决定继续有效。

实施情况：公共连接/托管凭据/共享 token、统一业务回调、组织绑定与单向同步、三家通知、工作台入口及企业 RPC 通讯录/消息包均已实现并有定向本地测试。集成管理按 ADR-007 上下分区装配，管理员第三方登录查看/解绑已接入原用户详情。真实企业联调、真实数据迁移和多节点发布演练尚未执行；剩余代码及治理差距由设计正文 §18 维护。

人员绑定处理：保留安全登录绑定与组织关联的领域边界，关系核对和冲突纠正由管理员负责；在原用户详情补齐第三方登录查看和解绑，复用已有管理员 API、绑定服务及用户管理权限。此前提出的自动协同绑定方向不纳入本期，具体规则见[设计正文 §6.3.1](../design/cross-cutting/enterprise-collaboration-integration.md#631-管理员查看与解绑第三方登录已实现本地验证通过)。该补充保持既定职责划分，界面及管理员 API 已有本地行为验证。

## 背景

现有三平台集成主要放在审批模块中，已经复用安全模块的 SSO 绑定解析企业成员。通知另有渠道员工地址关联，缺少企业连接作用域。只沿登录绑定建立成员关系，无法覆盖尚未登录的员工、部门绑定以及外部目录同步。

平台同时已有通知渠道 SPI、组织管理、应用路由与认证、JAR RPC 元数据加载机制。上述能力可以承接集成扩展，无须先建设通用待办中心或新的插件运行时。

## 决定

1. 通过既有领域扩展目录绑定/单向同步、通知渠道、工作台访问和按平台/API 能力组交付的 RPC 包；复用企业连接，领域分别拥有业务状态。
2. 外部部门→Department、外部成员→Employee 的关联由组织模块维护，绑定可以独立于同步和用户登录存在。Employee↔User 沿用现有关联，SSO 登录绑定仍由安全模块验证和维护，目录导入不授予登录和角色权限。
3. 通过原正式身份解析端口组合关系，冲突和歧义须拒绝，不给审批、通知分别维护相同成员关系。当前默认 SSO 解析的扩展和历史通知地址迁移应在同一正式链路完成。
4. RPC 包沿原元数据/Builder/执行器机制发现；引入包获得接口定义，配置连接及权限后才能调用。接口定义与具体企业连接分离，凭据及 token 按连接和用途隔离，副作用恢复仍归调用领域。
5. 插件沿 Maven 模块/JAR、Java SPI 和 AutoConfiguration 装配，安装后重启生效。统一管理入口采用对象列表，按类型和接入方向筛选；复用各模块的配置与受控命令，详情导航、表单及操作流程另行确认。（其中混合列表选择已被 ADR-007 的上下分区替代。）

### 2026-11-16：职责与依赖边界细化

本次细化沿用上述决定，相关公共基础与领域适配已实现，验证边界见本文实施情况。

- 从审批抽取公共连接与协议基础时，同时解除对审批连接类型、审批 Provider 和审批 runtime 的依赖。企业登录沿原安全端口独立装配，不要求安装审批；继续使用原配置与单一发现链路。
- 成员账号解析由组织侧适配实现既有安全接口，读取同一组织关联和原 Employee↔User 关系。Employee 地址保留组织查询视角，不强制开户；明确 RBAC 默认解析器让位，公共连接底座不接管组织关系。
- 通知渠道沿原扩展机制提供必要的地址解析，原入口组合；新增渠道 JAR 不要求宿主增加供应商分支。通知模板、分发、投递及恢复继续归原通知模块。
- 企业 RPC 凭据适配单向使用共享连接/token；领域可复用 API 包，底座不反向依赖企业 API 包或企业凭据插件。业务恢复和完成条件保留在原领域。
- 登录回调归安全链路；业务回调仅共享实际复用的验证和交付，审批事件及动作事实留审批。工作台入口组合原认证、绑定、路由和权限检查。

精确接口、模块边界和迁移要求由设计正文 §5–§8 维护，不将职责数直接转换为 JAR 数。

### 2026-11-16：公共机制与回调插件

- 凭据保护沿原配置管理策略、事务/CAS 和 SecretResolver 装配扩展，补齐加密及连接/凭据一致读取，不另建存储或配置中心。具体记录字段、算法和主密钥运维仍为实施细则建议。
- 提取既有应用级 token 机制，按连接、令牌种类和有效凭据代次隔离；减少等价版本的重复缓存键。用户令牌继续归安全链路，不引入通用 token 服务。
- 安全重试约束落实在原 RPC 执行入口；供应商业务错误由协议适配解释，必要调用事实转换为原通知/审批结果。业务完成条件、幂等及恢复仍归各领域，不新增通用业务 Outbox 或重试引擎。
- 业务回调本期提供统一入口，供应商插件贡献验证和响应协议，业务插件声明关注的 provider、事件类型和交付方式。沿原 SPI/AutoConfiguration 发现，安装 JAR 后重启生效；异步事件可有多个订阅者，同步命令只能有一个 handler，注册冲突明确失败。
- 异步回调先由全部匹配插件沿原领域机制持久受理，再按供应商协议 ACK；部分插件已受理后的重投由各自幂等机制处理。审批 receipt/inbox 保留审批所有权，统一入口不要求公共事件表或通用 worker。独立公共交付存储按后续真实需求设计，OAuth 回调继续沿原安全链路。

统一入口和插件关注声明的目标不再以出现第二个领域消费者为前提；公共持久交付平台仍为条件性后续。协议、注册及可靠受理规则见设计正文 §6.4，已实现，本地回调迁移测试已通过，供应商后台地址切换仍待验。

### 2026-11-16：模块粒度与最小装配

- 公共 core/runtime、每家供应商基础以及真正有领域依赖的通知/审批/目录插件按独立安装需要拆分。轻量登录 profile/builder 可随 provider，公共 resolver 随公共 runtime，组织账号适配优先随原组织 runtime；不为职责数量机械新增 JAR。
- API 能力组沿原 RPC 元数据 JAR 交付，共用企业凭据适配并委托 provider 协议；不为每个 API 建 core/runtime/starter/Registry，不复制 token 缓存或请求定义。全量选择沿原 ability-all-runtime/产品组合，不要求另建 connector-all。
- 先沿原渠道扩展迁移 AppRuntime 的地址解析，再解除其对 notification-channel-all 的编译依赖；完整产品继续由原组合装配渠道，原非企业地址行为须保持。
- 原 SPI/Center 与 AutoConfiguration 的发现、托管实例和生命周期在正式消费入口接通，避免重复构造和全局静态 Bean 缓存；不全面替换各领域已有优先级合同。同步分开公共/provider 和领域扫描、模型与 worker，能力枚举不提前拉 token。
- 以真实缺少无关 JAR 的最小登录、通知、RPC、业务回调、应用接入及工作区组合验证独立性。完整产品关闭开关不替代该验证；源码审查尚不证明这些组合运行通过。

上述方向已确认，细节及装配验证见设计正文 §5.1–§5.4、§8 和 §13.1，相关装配及行为已有实现，本地测试通过；真实产品发布验证仍按设计正文执行。

### 2026-11-16：RPC 企业应用令牌认证

- 沿原 `RPCAuthCredentialBuilder` 增加企业应用令牌凭据实现，暂名 `EnterpriseAccessToken`。API 定义引用认证名称，认证定义描述供应商、应用令牌种类及注入方式，企业连接独立保存身份和凭据；同协议 API 共用认证定义。
- 企业 Builder 由原 Center 发现和选择，企业凭据继承原 `AbstractAccessTokenRPCAuthCredential` 复用注入机制，委托共享企业访问基础获取应用令牌。不为每个 API 增加 Java Builder，不叠加动态 token RPC 或第二份缓存；原通用凭据类型继续保留，用户 OAuth 令牌继续归安全链路。
- 实际连接及凭据代次来自经过服务端授权的调用资源，业务参数不能覆盖；原 Builder 已有资源重载，本次接通原 SPI 的托管依赖及资源组装。加载认证定义不请求 token，运行时按需获取，缺失/歧义连接或认证失败即终止调用。
- 令牌放置沿原元数据表达具体 API 协议差异；刷新 token 不绕过原副作用重试约束。精确类型签名、资源合同以及编辑校验、测试、凭据使用范围和脱敏细则仍需细化。

方向已确认并已有实现；示意元数据和生命周期由设计正文 §7.8.1 维护。

### 2026-11-16：RPC 执行与工具链补充约束

六项原则已沿原执行/编辑/测试机制实现：凭据使用权与最终请求目标分别受控；API 的应用形态、令牌及 scope 匹配；正常、嵌套和测试调用取得可信资源且不捕获全局旧上下文；新类型的编辑/校验/运行支持随模块交付；测试明确真实目标、权限和效果并保护正式配置/共享缓存；日志、异常及测试证据强制脱敏。

约束落在原凭据 SPI、资源、执行、编辑校验及日志/测试机制。当前类型为 EnterpriseAccessToken，首批为三家通讯录及消息 API；真实 scope 和效果待企业验证，详见设计正文 §7.8.2。

### 2026-11-16：领域各自生效，撤销跨领域统一激活

保存、诊断检查、启停和执行分别沿所属模块的受控入口进行。配置保存保留相应 Schema/凭据、权限及事务/CAS 校验；检查按具体能力返回当次诊断，不自动切换无关能力的启停状态，也不替代执行时的真实授权和凭据检查。

审批保留原映射的草稿/校验/激活及运行绑定版本；登录、通知、组织同步、RPC 和客户端/DCR 保留各自正式模型与生效机制。原跨领域统一激活草案撤回，不新增通用 Mapping 表、激活服务或要求每个插件实现统一版本接口。同一企业/应用的密钥轮换按原凭据规则处理，不因此强制重新发布全部领域配置。方向已确认并沿各领域实现，细则见设计正文 §9.2。

## 影响与取舍

组织关联与登录绑定分别表达资料归属和认证事实，已有以 SSO 为唯一成员来源的默认解析需扩展，但不能用新的独立审批映射替代它。通知地址解析需连接感知并可由渠道扩展，防止增加 JAR 时仍修改宿主固定清单。

绑定/同步、通知、入口和 RPC 包可以按实际能力逐步交付。统一待办中心、原生待办同步、全过程代理审批、目录双向写回和入口自动发布属于独立后续需求，不作为本期前置工程。

本决定细化[企业协作平台集成架构](../design/cross-cutting/enterprise-collaboration-integration.md)的组织关联及能力装配范围；实现、迁移和验收要求在该正文维护。未替代既有编号 ADR。
