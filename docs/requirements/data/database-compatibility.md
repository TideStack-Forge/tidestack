# 显式数据库兼容能力

## 用户故事

- 作为需要在既有数据库环境中落地平台的实施人员，我希望选择已经验证支持的数据库后，模型迁移和日常数据操作能正常工作，而不是为每个项目临时维护一套补丁。
- 作为在开发平台配置应用数据源的维护者，我希望能明确选择对应的数据库驱动和连接信息，并让生成的应用继续使用同一套数据模型与页面能力。
- 作为负责平台交付和升级的人，我希望新增数据库兼容能力不会顺带切换默认数据库、改变现有容器环境或把受限制的驱动混入标准交付物。

## 为什么需要

不同组织往往已经有固定的数据库选型。平台如果只在默认数据库上可用，项目落地就会变成临时改 SQL、手工改迁移脚本和单独维护部署包；这些补丁还会在升级时反复失效。数据库兼容需要成为可验证、可选择的正式能力，而不是散落在项目分支里的例外处理。

## 怎么解决

平台为经过验证的数据库提供一致的数据建模、迁移、查询和数据源配置体验。使用者显式选择目标数据库并提供连接前提后，平台沿用同一条正式能力链路工作；新增兼容范围不会自动改变其他环境的默认选择。

## 边界

- 它不表示任意数据库都能自动兼容；每种数据库仍需要明确的支持范围和真实环境验证。
- 它不负责切换平台默认数据库，也不要求开发容器、部署脚本或标准镜像跟随某个兼容目标改变。
- 它不默认打包供应商 JDBC driver；使用受授权或受分发限制的驱动时，由部署方显式提供。
- 它保证的是平台已经验证的核心建模、迁移和数据访问路径，不承诺未验证的数据库专有高级能力。
- 使用前提是目标数据库、连接信息和所需 driver 已由部署环境准备好。
