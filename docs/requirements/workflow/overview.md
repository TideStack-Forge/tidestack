# 审批流总体需求

## 用户故事

- 作为流程设计者，我希望先把默认审批流程设计出来并沉淀为产品能力，而不是把规则散在表格、群消息或口头约定里。
- 作为应用部署后的管理员，我希望能在已发布流程上继续做定制和接管，而不是每次调整都重新从零设计。
- 作为业务申请人，我希望从统一入口发起审批并看到当前进度，而不是反复私聊确认卡在哪一步。
- 作为审批人，我希望直接看到申请上下文并完成处理，而不是自己猜这条申请该怎么流转。
- 作为支持人员，我希望能观察历史与运行中的实例、处理异常并留下完整记录，而不是出了问题再翻日志和导表。

## 为什么需要

审批不是一次性点击，而是一条会经过定义、发布、发起、处理、退回、跟踪和介入的业务链路。没有统一能力时，这条链路很容易被拆到表单、消息、人工约定和临时脚本里，最后谁该批、批到哪、为什么卡住、改动是否生效，都只能靠人追。

## 怎么解决

系统提供一套围绕审批闭环展开的统一能力。默认审批流程先在开发平台里设计，作为产品内置能力沉淀下来；部署到具体应用后，管理员可以在运行时继续定制、接管和发布。流程保存和流程生效分开，真正影响运行的只有已发布版本。业务对象只暴露一套稳定的审批状态投影，平台负责按实例结果把它维持在正确位置。运行中的实例、历史实例和异常介入也都在同一条能力链里管理。

## 参与者与职责边界

- 流程设计者：定义默认流程和基础规则。
- 部署后管理员：按应用实际情况调整、发布和下线流程。
- 业务申请人：发起审批、补充信息、跟踪进度。
- 审批人：处理待办、给出意见、推进流转。
- 支持/治理人员：观察实例、排查异常、做受控介入。

## 作用域

- 这份需求主要面向应用实例上下文，不面向平台外的临时协作。
- 同一个业务对象类型默认只对应一条主审批流程，不承诺让系统自动在多条候选流程里挑选。
- 同一个业务对象在同一时间只允许有一个运行中的审批实例，但可以保留多条历史实例。
- 新实例永远从当前已生效版本开始，已在运行中的实例不被新发布影响。
- 这份需求只承诺显式发起，不承诺后台规则、定时任务或外部事件自动开单。

## 分层来源与接管规则

- 默认流程来自开发平台，运行时定制来自应用实例。
- 同一流程标识在默认层和实例层表示同一条流程；实例层优先级更高。
- 实例层可以覆盖默认流程，也可以新增只存在于该实例的流程。
- 如果删除了实例层的覆盖项，默认流程应重新可见。
- 一旦某条流程被实例层接管，后续默认更新不再自动覆盖这个实例里的定制结果。
- 如果某条流程还没有被实例层接管，默认更新应自动反映到该实例的可见结果里。

## 发布与生效

- 保存流程不等于流程生效。
- 开发平台上的默认流程不需要发布语义；部署后的应用实例至少要发布一次才可开始使用。
- 只有已发布版本才能发起新实例。
- 重新发布只影响后续新实例，不回头改动正在运行的实例。
- 下线后不允许再新开实例，但历史和正在运行的实例仍要可追溯。
- 同一条流程的发布、重新发布和下线都按单流程粒度处理。

## 核心对象与生命周期

- 流程定义：描述这条审批要怎么走。
- 已发布版本：描述某一时刻真正可运行的定义。
- 流程实例：描述某次具体审批的运行过程和最终结果。
- 审批任务：描述当前需要谁处理、处理什么。

业务对象的审批状态和流程实例结果不能混成一个概念。流程实例的终态是事实来源，业务对象的审批状态只是对外展示和消费的投影。平台需要维护一个主审批状态承载位，并且可以在实例结果明确时做受控修复，但不能让业务侧随意改写事实再倒推实例结果。业务对象的审批状态也只是整体生命周期中的一个维度，不等于业务对象的全部状态。

## 任务处理与流转动作

- 审批人要能处理待办、转派、加签、退回和同类流转动作。
- 申请人要能做补充、撤回、重新提交等后续动作。
- 这些动作都应围绕当前实例状态展开，并留下可追溯记录。

## 观察与介入

- 系统要能看运行中实例，也要能看历史实例。
- 流程定义、已发布版本和运行中实例都应有稳定的只读查看面，便于设计者、管理员和支持人员在不进入编辑态的情况下确认当前规则、版本事实和实例走向。
- 异常介入包括强制终止、人工恢复、越权转派、补救推进和状态修复。
- 人工恢复只针对运行链路里的可补救异常，不负责修流程引擎底层故障。
- 所有介入都要有完整审计记录，默认采用追加式治理，而不是悄悄改掉原始结论。
- 高风险的“直接改写原始审批结果”不在本轮直接承诺范围。

## 前提条件与外部协同

- 业务对象需要先准备好表单、参与范围和基础权限，审批流才有稳定入口。
- 平台对外应保持流程能力与工作流引擎松耦合，业务侧面向平台契约，不直接依赖引擎原生标识。
- 对接外部工作流引擎时，需要能把平台里的流程标识和外部引擎标识对应起来。
- 内置默认审批能力仍然是产品基线，外部引擎接入只是扩展边界。

## 边界

- 它不替代纯自动执行逻辑，也不承接审批之后的自动后置处理。
- 它不负责通用报表、综合分析或和审批无关的仪表板。
- 它不把当前默认引擎的具体实现细节写进需求正文。
- 它不承载 V2 图结构语义、节点/边 contract、编辑器校验与交互细则；这些由长期 decision 和子 feature 规格承接。
- 它不承诺后台规则、定时任务或外部事件自动发起审批。
- 它不把没有明确业务入口的临时协作硬塞进审批流程。

## 能力分解 / 子需求索引

1. 流程定义与分层定制：默认流程设计（开发平台）、部署后定制（运行时实例）
2. 发布与生效：首次发布、重新发布、下线、接管后的持续管理
3. 发起与进度：流程发起与提交、实例进度与结果跟踪
4. 任务处理与流转动作：审批人与处理人任务动作、申请人后续动作
5. 观察与介入：实例观察与追溯、异常介入与治理动作
