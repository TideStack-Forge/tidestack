# 让系统自动执行逻辑能被建模、运行和排查

诊断通过读态 `validationSnapshot` 返回。字段合同由逻辑流的[端口与数据契约](../../core/ouroboros-logicflow/design/ports-and-data-contracts/overview.md)定义。

## 用户故事

- 作为负责搭业务自动化的人，我希望把一段系统自动执行逻辑做成可复用的流程资产，同一份流程既能被不同触发场景复用，也能被别的流程正式引用，而不是每个入口都各写一遍规则。
- 作为开发平台的维护者，我希望流程保存后先变成正式、稳定的交付物，再被运行环境加载执行，而不是让运行时直接依赖编辑器会话、本地缓存或开发平台进程里的临时对象。
- 作为接手低代码应用的人，我希望图上看到的入口、分支、成功收口、失败收口和真正运行时的语义一致，而不是编辑器里能画、保存时能过、运行时却按另一套规则执行。
- 作为同时要负责设计态和运行态的人，我希望设计时那套更丰富的模型在进入运行环境前先收敛成一份稳定、可执行、只保留必要语义的表达，而不是把布局、编辑辅助信息和临时状态原样带进执行过程。
- 作为排查问题的维护者，我希望保存模型后马上看到后端诊断；如果问题来自子流程或上下游约定断了，系统还要告诉我是沿着哪条引用链路坏掉的，而不是只丢给我一个模糊名字让我自己倒推。
- 作为做联调和回归的人，我希望流程执行时不只是告诉我成了还是没成，还能稳定看到节点什么时候开始、什么时候结束、哪里失败了，以及最后的结果摘要，这样前后端和运行时一旦跑偏，我能尽快发现。
- 作为维护流程资产的人，我希望改动一条流程前能尽可能知道会影响哪些父流程和接入点，而不是上线后再靠联调撞出断裂。

## 运行时检查与覆盖（已确认）

运行维护者需要在应用运行环境观察已有逻辑流的部署默认、持久覆盖和实际执行版本，并复用正式编辑器修改覆盖。管理范围仅限当前应用；实例视图表示同一应用的运行副本，不提供跨应用管理。首期不新增模型，锁定名称、启用状态、流程公开输入输出类型和 Schema；允许改动内部节点、连线和属性。未知来源、不完整来源、冲突来源或不能确认实际执行元数据时只读。

- LF-RM-OBSERVE：列表可搜索和筛选，禁用来源仍可观察但不成为可编辑默认；详情区分来源、默认、覆盖、当前实例与诊断，默认指最后成功完整 Context 的部署目录。
- LF-RM-WRITE：检查只构建不执行；保存、撤销和恢复操作前态采用持久 CAS，旧页面冲突保留草稿，重复请求可幂等重放，权限分别控制读、编辑和重新核对。
- LF-RM-APPLY：保存后异步独立刷新逻辑流，父子流同代切换，已开始的调用保留原对象；失败保留旧代且可恢复。
- LF-RM-CLUSTER：各实例观察同一持久目标并独立确认应用，重启加载覆盖；回执区分已提交与已应用，历史 boot 记录不等于在线成员。
- LF-RM-LAZY：普通列表和详情不下载画布，开图或编辑时才加载；加载失败可人工重试，关闭后不迟到挂载。共享资产复用同一微前端身份，旧页跨资产升级仍可加载其所属版本的异步块。

运维详情与逐流程观测要求已实现，验收状态随功能介绍维护。

- LF-RM-OPS-DETAIL：模型详情按运维任务重新组织，先显示实际执行版本、持久目标与实例分歧，再提供失败处理、恢复、变更追溯和模型来源；完整标识与原始正文按需展开。关闭运行采集不能隐藏模型校验、来源错误和应用失败。
- LF-RM-OBS-PER-FLOW：运行监控和执行诊断可按单个逻辑流独立开关，未配置一律关闭；开启一个流程不能自动开启其他流程。关闭时不采集该流程的运行统计或节点诊断，不把未采集显示为零调用或全部成功。开关状态与各实例实际采用状态分别表达。

运维详情与采集策略的机制、时长、容量、权限和保留周期见[运行手册](../runbooks/logicflow-runtime-manage.md)。机制与界面取舍见[运行时管理设计](../design/cross-cutting/logicflow-runtime-management.md)。

服务器草稿、沙箱测试和正式发布编排不在首期内。实际验证状态见[功能介绍](../features/logicflow.md)，执行证据归实施任务。

## 为什么需要

很多系统自动逻辑不是一段直线代码，而是由多个步骤、分支、输入输出、失败处理和子流程引用拼起来的。没有统一的逻辑编排能力时，团队很容易把规则散在脚本、接口调用、页面配置和人的记忆里：谁先执行、失败后怎么办、某个节点为什么没跑、父流程依赖了哪些子流程、改了一个地方会影响谁，最后都只能靠经验和临时排查补上。更麻烦的是，设计时看到的流程、正式交付出去的内容和运行时真正拿来执行的内容如果不是同一回事，编辑器、开发平台和运行环境看到的就会是三套事实。逻辑一复杂，这种偏差会越积越多，流程越复用越难治理。

## 怎么解决

系统提供一套统一的逻辑编排能力。维护者围绕清晰的入口、成功输出和失败出口来建模，让同一份流程既能被不同触发场景复用，也能作为正式流程资产被别的流程引用。流程保存后，不会停留在编辑器会话或本地临时状态里，而会先沉淀成平台认可的正式模型，再沿既有交付链进入运行环境。真正执行前，系统还会把设计时那套更丰富的表达收敛成一份稳定、只保留运行所需语义的执行表示，避免把布局、编辑辅助信息和临时诊断直接带进容器。设计时编辑器本身也会把常用 authoring chrome 收口成稳定表面：toolbar 负责重新打开节点面板和属性面板，校验提示继续消费后端诊断真相，节点 / 连线取消选中后关闭属性面板而不是偷偷切回流程级属性；当后端诊断已经能稳定定位到具体字段时，属性面板会直接把错误挂到对应表单字段上，定位不到字段的错误则继续留在面板告警区。保存阶段会尽早给出诊断，帮助建模者发现结构问题、依赖断点和输入输出约定不匹配；真正能不能执行，仍由正式生效、能力边界和失败规则共同决定。运行后，系统会把关键错误、依赖关系和节点级调试线索稳定暴露出来，方便联调、排障和回归。流程资产的版本、生效和发布治理则继续复用平台统一能力，而不是在 LogicFlow 内部再做一套。

## 边界

- 它不负责替代需要人工判断、审批和待办流转的流程；那类场景应优先交给审批流等人参与能力。
- 它服务的是系统自动执行逻辑编排，不是通用画图工具；编辑器是带约束的建模界面，不是想怎么画就怎么画的自由画布。
- 画图时看到的东西、正式交付出去的东西、运行时真正执行的东西不是一回事；编辑器里的临时状态、宿主会话数据和未正式沉淀的本地改动，不应直接成为运行容器的执行事实。
- 默认流程由开发平台交付为正式模型；运行时管理允许持久覆盖后经同一 Factory 构建和原发布点应用。运行环境不依赖开发平台进程里的临时对象。
- 设计时那套更丰富的模型不会原样带进运行环境；运行时只消费收敛后的稳定执行表示和输入输出约定，布局细节、编辑辅助信息、临时诊断和宿主编排状态都不算运行语义。
- 它当前处理的是一次触发下的自动执行，不负责那类需要长期挂着、人工接手、暂停恢复、自动重试、补偿、长事务、统一超时或取消治理的流程。
- 它不负责承接完整业务页面、主应用路由或通用壳层体验；它提供的是逻辑编排与执行能力，不是整个产品界面。
- 它当前的设计时壳层只定义 authoring chrome contract，对齐审批流等同类编辑器的 toolbar / panel / diagnostics 行为，不意味着引入第二套流程语义、第二套运行时入口或跨包复用别的编辑器实现。
- 它不适合承接没有清晰输入、输出和执行边界的临时自动化；如果连流程想解决什么问题都说不清，先上图只会把混乱搬进系统。
- 它不负责替代业务系统自己的领域规则定义；业务仍需要先明确数据模型、节点能力和调用边界，逻辑流只是把这些能力编排起来。
- 使用前提是相关节点能力、运行环境和接入上下文已经准备好，否则即使图能画出来，也会在执行、诊断或联调时反复返工。
- 它只编排当前应用、当前上下文里已经正式暴露的节点能力和子流程，不应成为越权调用的侧门。
- 主流程、节点和子流程之间要靠清楚的输入输出约定衔接，不能靠隐式共享上下文硬接；保存成功不等于模型一定能执行，建模阶段的诊断也不直接替代运行时的放行判断。
- 每条流程都必须围绕清晰入口、成功输出和失败出口建模。参数缺失、模型本身不合法、没有走到任何成功收口、正式生效流程或其依赖子流程不合法等情况，都应显式失败，而不是偷偷兜底、静默回退，或悄悄换一条别的流程遮住问题。
- 图里的错误恢复入口只负责已经开始执行后的补救，不负责替模型本身兜底；恢复成功也必须走到明确成功收口。更细的恢复语义和未来正式错误处理入口，会由独立决策和后续设计继续钉死。
- 当前控制流和子流程组合都以无环编排为边界；它不承诺图内通用循环，也不支持子流程递归或循环依赖。需要重试、重复尝试或严格补偿时，应通过显式能力表达，而不是依赖单次执行里的隐式重入。
- 子流程复用是正式的流程资产引用关系，不是运行时任意跳转；依赖断裂应尽可能在建模、保存、生效前提前暴露，能不能执行也应覆盖整条直接 / 间接依赖链，而不是只看眼前那一跳。
- 多成功终点表达的是不同成功收口，不等于真正的提前终止或取消语义。
- 只有存在直接或间接依赖链时，图上的前后才构成运行时先后；对没有依赖关系的节点，即使视觉上看起来一前一后，也不承诺按那个视觉顺序执行。
- 主流程失败或切入错误恢复入口，不等于其他已调度且无依赖关系的分支副作用会自动被阻止、取消或回滚；如果业务要求严格的副作用隔离、顺序或一致性，必须通过显式依赖、外部事务、幂等或补偿策略治理。
- 运行期调试和诊断只是联调、排障和回归时的观察面，不会反过来改变主执行语义，也不把自己做成长期审计系统。它应稳定暴露关键错误、依赖关系和调用链线索，但不默认承诺完整回放、全量原始输入输出透传或按视觉顺序排好的全局时间线。
- 流程资产依赖和影响分析应尽可能在保存、启用或发布前，让维护者看到直接 / 间接引用关系、依赖路径和断点，但不承诺对所有动态变化都做 100% 穷尽；是否因此禁止启用或发布，交给平台统一治理能力决定。
- 流程资产和节点输入输出约定的演进不能悄悄换意思；如果出现不兼容变化，系统应显式暴露断裂、要求迁移或阻止误用，而不是让旧流程在不知情的情况下换了一套语义。
