# 让统计分析从数据准备走到最终交付

## 用户故事

- 作为负责搭分析页面的人，我希望围绕同一套分析能力组织数据集、图表和仪表板，而不是在一堆旧入口和技术对象名之间来回猜哪个才是主路径。
- 作为业务分析或配置人员，我希望先把数据口径、筛选条件和展示方式整理清楚，再逐步交付分析页面，而不是每次都从零拼查询、报表和可视化。
- 作为最终业务使用者，我希望进入一个明确的分析页面查看指标、图表和结果，而不是自己判断该去综合查询、统计报表还是别的历史入口。
- 作为负责治理的人，我希望分析资产能沿着一条清晰链路被维护和发布，而不是对象很多、名字很多，但出了问题没人说得清上游下游关系。

## 为什么需要

分析能力最怕的不是图表不够多，而是入口、对象和心智全都散开。数据、查询、图表和仪表板如果各自独立生长，最后用户只能靠历史术语和个人经验判断“这次到底该建什么、去哪看、怎么交付”。一旦名字和入口混乱，返工通常不是因为算不出数据，而是因为对象边界不清、页面路径割裂、交付结果不稳定。

## 怎么解决

系统把统计分析收敛成一条更稳定的分析主线：先围绕数据集定义事实来源和参数边界，再把数据组织成图表，最后组合成交付给业务的仪表板或运行时页面。当前这组能力仍在继续收口历史入口和旧命名，但对使用者来说，真正需要抓住的是“数据集、图表、仪表板”这一条可持续演进的分析链路，而不是被旧查询页、旧报表页或零散菜单牵着走。

## 边界

- 它不等于所有查询页面的总入口；更偏业务明细、事务处理或临时检索的页面，不应该默认归进统计分析主路径。
- 它不负责替代底层业务数据建模、组织权限或流程处理；统计分析依赖这些能力提供稳定数据和访问边界，但不把它们并入自己。
- 它不承诺一上来就覆盖复杂 BI 平台式能力；第一次落地时更适合先交付清晰的数据集、图表和仪表板闭环。
- 使用前提是数据口径、目标受众、筛选条件和交付场景已经基本明确，否则最容易反复返工的会是对象边界，而不是页面样式。
