# 让综合查询把筛选、结果和处理入口放在同一页

## 用户故事

- 作为业务人员或支持人员，我希望按条件快速筛出一批业务记录并直接查看结果，而不是每次都找人导数据、翻多个页面或靠经验猜条件。
- 作为负责配置应用的人，我希望把筛选项、结果列、导出能力和页面跳转整理成一张可复用的查询页，而不是每个场景都单独拼一套临时页面。
- 作为需要跟进问题单据的人，我希望在查询结果里直接进入详情、执行后续动作或导出允许导出的数据，而不是先查一遍、再去别的地方重新找同一批记录。
- 作为负责治理数据访问的人，我希望不同角色只能看到和导出被允许的结果，而不是查询一开放就默认所有人都能拿到全部明细。

## 为什么需要

很多业务场景要解决的不是“看总体趋势”，而是“把符合条件的那批记录找出来，然后继续处理”。如果没有统一的综合查询能力，团队通常只能在临时列表页、后台导表、手工筛选和口头需求之间来回折腾。最后最耗时间的往往不是数据本身，而是每次都要重新确认筛选条件、展示字段、导出范围和后续跳转入口。

## 怎么解决

系统提供一类面向业务明细查询的统一能力：先由配置者定义好筛选条件、结果字段、导出边界和后续入口，再让最终用户在运行时页面里直接执行查询、查看结果、导出允许导出的数据，并进入下一步处理。当前这组能力仍在和统计分析产品域做边界收口，但对使用者来说，它稳定解决的始终是“查到一批记录并继续处理”的问题，而不是指标展示或仪表板交付。

## 边界

- 它不负责替代统计分析中的图表、指标卡和仪表板；如果目标是看趋势、看分布或做分析展示，应该优先走统计分析主路径。
- 它不提供面向最终用户的自由 SQL、任意建模或无限制数据拼接；查询边界应由预先定义好的数据口径和权限控制来约束。
- 它不替代具体业务详情页、审批页或编辑页；综合查询负责“找到哪些记录”和“从哪里进入下一步”，不负责承接所有业务处理本身。
- 使用前提是查询对象、筛选条件、展示字段和权限范围已经基本明确，否则查询页很容易退化成另一个谁都不敢改的临时大列表。
