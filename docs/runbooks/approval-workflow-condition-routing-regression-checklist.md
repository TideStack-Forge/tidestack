# 审批流条件路由缺陷：回归排查清单

> 适用于当前 Flowable 条件表达式与条件路由排查。当前语义以[定义合同](../../core/ouroboros-approval-workflow/design/definition-metadata-and-graph-contracts/overview.md)及源码为准。

## 1. 修的是什么

审批流的条件分支最终由 Flowable 的 JUEL 求值。历史上有四处缺陷会让**条件静默失效**——
流程照常流转、不报错、但走错分支：

| # | 缺陷 | 表现 |
|---|---|---|
| 1 | **条件对象给字符串右值预加了一层双引号**（`CompareCondition.toExpression`），与操作符的字面量引号叠加成 `level == '"特级"'` | **所有字符串条件恒假**——这是主因，且位于操作符之上的一层，只测操作符的用例看不出来 |
| 2 | 操作符渲染字符串字面量时不加引号：生成 `level.equals(特级)`，`特级` 被 JUEL 当作变量名 | 同样导致字符串条件恒假（与 #1 叠加） |
| 3 | 集合判定用了 JUEL 不支持的形态：`left.contains({'a','b'})` | 词法错误（`{a,b}` 不合法）、`in` 运算符不支持、`[a,b]` 是数组没有 `contains`；已改为等值析取链 |
| 4 | 分支判定（`FlowableFlowDefinitionService`）用裸表达式求值，缺 `${...}` 承载形态 | 求值原样返回字符串 → `Converter.toBoolean` 取默认 false → **"按分支匹配节点"恒为空** |

四点里 #1 与 #2 会叠加，所以**排查时不要只看操作符层**：条件对象的产出才是引擎真正求值的东西。

第 4 条影响的是"按变量推断会走哪些节点"这类**只读视图**（如发起前展示将要经过的审批节点），
第 1、2、3 条影响的是**引擎真实路由**。

## 2. 哪些流程需要复核

只要同时满足"用了条件分支"+"分支条件是字符串或集合判定"，就属于受影响范围。
逐项对照：

| 复核项 | 说明 |
|---|---|
| 条件里出现**字符串取值**的比较 | 受影响最广。`equal`/`not_equal`/`select_equals`/`select_not_equals` 对字符串一律恒假 |
| 条件是 **"字段包含某集合中的值"** | `select_any_in`/`select_not_any_in` 因形态非法而报错或恒假 |
| 条件是**文本匹配** | `like`（子串）/`starts_with`/`ends_with` 恒假 |
| 条件是 **between 区间** | 若边界是**字符串**（如日期）则恒假；数字边界不受影响 |
| 条件用**数字**做大于/小于/相等 | **不受影响**（数字不需要引号） |
| 没有条件分支的线性流程 | 不受影响 |
| 只有条件分支但条件恒为真的兜底边 | 行为不变，但建议确认兜底边是不是在掩盖问题 |

**前端 bundle 确实会输出这些操作符**（`select_any_in` / `select_not_any_in` /
`not_between` / `not_like` / `starts_with` / `ends_with` / `select_equals` / `not_equal`），
所以"设计器里配过字符串条件"的流程都要查。

## 3. 怎么查

### 3.1 从定义文件/数据库里定位

审批流定义里的条件形如：

```json
{ "left": { "type": "field", "field": "level" }, "op": "select_any_in", "right": ["特级","一级"] }
```

排查要点：

1. `op` 是否属于受影响操作符（见上表第一列）；
2. `right` 是**字符串**还是数字——数字不受影响；
3. 记录的 `right` 是**数组**的（`select_any_in`/`between` 等）也要查。

### 3.2 从运行数据里定位（更可靠）

比看定义更直接的判据是**业务表现**：

| 现象 | 很可能是本缺陷 |
|---|---|
| 某个条件分支**从来没有进过**（历史实例全走同一条路） | 该分支条件恒假 |
| 流程总是走"兜底/默认"分支 | 前面所有条件边都没命中 |
| 按金额走的路是对的，按**类型/等级/状态**走的路不对 | 字符串条件恒假 |
| 发起前预览的"将要经过的审批节点"与实际不符，或预览为空 | 第 4 条缺陷（分支判定恒空） |
| 修好之后同一个定义的路由结果变了 | **预期行为**，不是新回归 |

### 3.3 修复前后的对照方法

对同一个流程定义、同一组变量：

1. 用**修复前**的版本发起一次，记录落到哪个审批节点；
2. 用**修复后**的版本发起一次，记录落到哪个节点；
3. 若两者不同，说明这个流程此前走错了分支——应以**修复后**的结果为准，
   并回溯已产生的在途实例是否需要用正确路径处理。

`FlowableConditionRoutingIntegrationTest` 在当前实现上使用同一份定义与不同变量断言落到的节点；历史版本对照需另建隔离环境。

## 4. 修复后新暴露出来的错误（不是回归）

修复把"静默恒假"变成了"显式报错"，因此可能**新增**启动期失败。这类报错说明定义本身有问题：

| 报错 | 含义 | 处理 |
|---|---|---|
| `Error while evaluating expression: ${... ` | 字段类型与操作符右值不匹配，例如**数值字段被拿去和字符串集合比较** | 修正定义：数值字段用数值右值，或改用字符串字段 |
| `Unknown property used in expression: ${...}` | 条件引用的字段**没有作为实例变量传入** | 检查发起时是否把该字段写进实例变量（表单字段不等于实例变量） |
| `No outgoing sequence flow of the exclusive gateway '...' could be selected` | 该分流**所有出边都是条件边且都不命中** | 给分流补一条兜底边（无条件边，或 `is_empty` 之类的显式兜底） |
| `FlowDefinitionCodecException: ... 右操作数必须是数组` | `select_any_in`/`between` 的右值不是数组、或 `between` 不是两个元素 | 修正定义为数组形态 |

前两类是"修复前会静默走错、修复后直接拒绝"——**报错是期望行为**。

## 4.1 否定条件与兜底边

`not_equal` 的条件语义与其他比较条件共用 `CompareCondition → OpEnum`。不能仅凭“未进入该分支”判定操作符失效：先检查实例变量、最终 `${...}` 表达式与全部出边。所有条件均不命中且没有可选兜底边时，Flowable 会抛出 `No outgoing sequence flow ... could be selected`。

`FlowableConditionRoutingIntegrationTest` 已包含否定比较命中及显式兜底边用例。它验证当前实现的路由结果，不是运行旧版本与新版本的对照测试，也不证明当前环境已通过。目标引擎版本和运行环境须分别复跑。

## 5. 防复发

| 防线 | 位置 |
|---|---|
| 操作符求值回归 | `ConditionExpressionEvaluationTest`（flowable 模块，13 个用例，命中与不命中都断言；其中 2 个以 `CompareCondition` 为入口，专门防 #1 复发） |
| 端到端路由回归 | `FlowableConditionRoutingIntegrationTest`（4 个用例，定义→转译→部署→启动→落节点；含集合命中、否定比较命中、兜底边、类型不匹配报错） |
| 词表与语义契约 | `design/definition-metadata-and-graph-contracts/overview.md` §5.2「操作符右侧取值约定」与「引擎表达式形态」 |
| 操作符名解析 | `OpEnumTest`（未登记操作符显式失败，不静默降级） |

## 6. 条件求值的验证方法

1. **判断"条件是否生效"必须看求值结果，不能看表达式字符串**。裸表达式（不带 `${...}`）
   交给 `ExpressionManager.createExpression` 会被**原样当成字面量返回**，既不求值也不报错——
   这正是第 4 条缺陷能长期隐藏的原因。
2. **测试里构造流程定义要用 Jackson，不要手拼 JSON**。条件里的引号与集合字面量手拼极易
   产出非法 JSON，报出来的却是 Jackson 的 `Unexpected character`，与真正的缺陷毫无关系。
