# 逻辑流运行时管理

本模块在应用运行环境维护已部署流程的持久覆盖。默认模型仍由原部署链交付；保存成功和各实例应用成功分别核对。模块入口与依赖见 [README](../../ability/ouroboros-logicflow-runtime-manage/README.md)，独立刷新机制见[生命周期](../../core/ouroboros-logicflow/design/model-lifecycle/overview.md#9-逻辑流独立刷新)。

## 装配与权限

`ouroboros-ability-all-runtime` 包含管理模块，独立装配也可选择 `ouroboros-logicflow-runtime-manage`。目标应用需要 LogicFlow runtime、typed data、事务管理器及平台原 UI、权限、微前端部署链。八个 `sys_runtime_flow_*` 数据模型由原数据模型迁移机制建表。不要通过外部 SQL 或另建通用数据 API 改写它们；写入必须经过管理服务的事务与集合 CAS。

系统设置入口为 `/system-setting/logicflows`。分别分配 `systemSetting.logicflow.read`、`.edit`、`.reload`、`.observation.read`、`.observation.manage`；写和重新核对同时需要 read。编辑权限允许修改可执行逻辑，应按应用管理员职责分配。后端每个接口均独立检查可信登录身份，按钮可见性不承担鉴权。

## 检查、覆盖与确认应用

1. 搜索流程，进入详情，对比部署默认、持久覆盖和当前实例。来源观察展示各来源优先级、启用状态、完整性和诊断；仅禁用定义仍可查看，但不会作为可编辑默认。当前实例的模型校验错误单独展示，可在受管条件满足时通过有效覆盖修复。只读原因说明来源不完整、冲突、未声明或实际执行 Provider 不受管理等限制。
2. 打开编辑覆盖，修改内部节点、连线和属性。首期锁定名称、启用状态和公开输入输出类型/Schema，最多 2 MB、2000 节点、8000 连线。
3. 检查候选，查看差异、诊断和父流程影响范围。检查通过表示可构建，不会执行流程，也不持久化。
4. 保存并应用。HTTP 202 表示覆盖与操作已持久提交；200 表示内容无变化、操作已记录。保留 operationId，按回执查询操作及后续实例状态。
5. 核对各实例的目标代次与已应用代次一致、状态 applied、回报时间有效。每个进程的 bootId 独立，历史启动记录可能已离线，不能把状态表当作在线成员注册表。

集合版本包含 epoch/revision，editToken 还绑定模型修订、默认目录来源戳与名称身份。旧页面遇到 409 时保留草稿，重新读取和对比后再次提交；不要自动换 token 覆盖别人修改。同一 actor、operationId 和完全相同请求可重放；修改请求内容必须使用新 operationId。

保存后每实例通过正式 Provider/Factory 独立重建逻辑流全集，父子流一次切换。已经取得的模型继续原对象。它不刷新数据模型、菜单或路由，也不重新扫描应用文件。默认指最后一次成功完整 Context 的部署默认；部署内容和依赖合同更新仍走原完整刷新。

## 撤销、恢复与失败处理

撤销覆盖会保留名称墓碑修订，并恢复最后成功 Context 的部署默认。恢复操作前态会读取同模型指定操作的 before，按当前 token 和合同重新检查，再形成新修订；它不是直接移动数据库版本指针。发生默认漂移时，先对比最新默认，决定保留覆盖还是撤销。

候选无效、完整 Context 竞争、发布等待超时或依赖暂不可用时，保留旧完成态。根据实例 error、desiredVersion、appliedVersion 和 reportedAt 定位；修正覆盖或默认依赖后可使用“重新核对”。该动作需要 reload，仅提示当前实例，其他实例靠各自核对周期收敛。动态键 `logicflow.runtimeManagement.pollSeconds` 默认 5 秒，允许 1–300 秒。

独立失败不会污染完整 Context 的可用门控。完整 Context 已失败时，管理 HTTP 也可能被全局门控拒绝；独立刷新不能恢复它，需沿原运维通道完成一次成功的完整刷新。数据库不可用时不把空覆盖当作成功；先恢复持久层再核对。不同节点部署默认不同会产生不同发布指纹，不能仅凭共享覆盖版本一致判断部署一致。

## 逐流程运行监控与诊断

详情按运行概览、实例、监控诊断、变更、模型来源组织。管理范围为当前应用及其共享存储中的运行副本。完整版本标识在“模型来源”的“版本与标识”中展开。实例回报超过 30 秒显示过期，回报时间与启动标识共同用于判断观察有效性。

每个流程的运行监控与详细诊断默认关闭。设置采集需要 `.observation.manage`，读取统计、样本和采集变更需要 `.observation.read`，均同时要求模型 read。监控记录已完成、失败、未完整与耗时直方图。详细诊断必须同时开启监控，时长可选 5、15、30 分钟，默认 15 分钟，每个启动实例、流程和采集批次最多接纳 100 次调用。已有诊断期间保存设置沿用原截止和批次，上限耗尽后通过关再开建立新批次。

采集在每次调用入口决定，父子流程各用自己的设置。子流程关闭时，父流程仍能记录调用节点的边界耗时。未采集的中间流程形成关联缺口，更深层已开启流程独立采集。样本仅包含节点名称、类型、作用域、时序、结果及异常类型，业务输入输出、异常消息和堆栈均不进入采集数据。

动态策略键 `logicflow.runtimeObservation.policies` 采用统一配置的一致快照与 expectedRevision CAS，配置和审计同事务提交。整份配置的并发冲突返回 409，保留表单并刷新核对。开关修订独立于模型修订，后台每 5 秒核对，各实例回报采用修订。到期事件由后台按采集批次幂等记录为 system-expiry。保存的监控可跨重启恢复，诊断继续使用原权威截止时间。

业务执行线程只更新有界内存数据。每个进程最多跟踪 1024 个调用、512 个分钟窗口、128 个待落库样本、8192 条活跃节点记录，每个调用最多 256 条节点记录。节点文本最多保留 200 字符。超额通过拒收、丢弃和截断状态体现。关闭及诊断到期后最长收尾 30 秒，超时记录未完整，保留已有历史。启用期间单次调用最长跟踪一小时。

后台持久化使用 typed data，窗口按稳定标识累计覆盖写入，样本按调用标识幂等写入。故障时暂停接纳新采集并有界收尾，业务继续沿原执行路径。恢复后后台重新采用配置。排障时先核对期望修订、实例采用修订和回报时间，再查看故障、拒收及丢弃计数。

统计默认保留 24 小时，诊断样本默认保留 1 小时。动态键分别为 `logicflow.runtimeObservation.metricRetentionHours` 与 `.runRetentionHours`，允许范围为 1–168 和 1–24 小时，后台每分钟清理。页面可查询近 15 或 60 分钟，支持启动实例和运行版本过滤。P95 是合并直方图后的桶上界，跨版本时逐行保留运行版本。未采集显示空态，读取失败显示错误，历史采集数据在关闭后继续可读。

运行样本按版本标识和轻量节点时序展示。当前模型图可从模型详情按需打开，旧样本的精确图快照尚未保存。

## 编辑器资产升级

编辑器元数据和 zip 唯一归属 `ouroboros-logicflow-editor-assets`，dev 与管理模块共同依赖。`package:sync` 生成 `/micro-logicflow-editor/<buildId>/` entry、带内容哈希的 JS/CSS 及异步块，列表和详情摘要只使用轻量注册代理，开图才加载画布。

部署新版本时保留仍被打开页面使用的旧版本目录，并核对静态代理能读取这些目录。旧页面稍后开图会请求旧版本异步块；不能只保留新 entry 或清空整个父目录。现有 Nginx 部署器清理目标目录，因此目标必须限定本次 buildId。保留周期和回收时机由实际发布策略决定，模块不自动删除旧目录。

加载失败可以人工重试；关闭后迟到响应不得挂载画布。运行时宿主关闭 dev 调试和代码提示，引用目录取当前运行环境，不回退开发平台地址。IDE 单独以 `publicPath=auto` 构建时保留原固定 app.js/app.css 入口。

## 可重复验证与边界

模块行为测试覆盖真实 H2 typed data、事务/CAS、权限及 HTTP 状态；[集成场景](../../testing/integration/feature/lowcode/logicflow-runtime-manage/harness.playbook.md)覆盖共享 H2 的双 JVM、重启及生产资产隔离浏览器。隔离宿主只替代平台壳层和可信身份传递，不能替代目标平台登录、真实数据库升级或生产静态代理验证。

实际发布前按目标应用原流程验证数据库迁移、角色授权、菜单和微前端装配、实例恢复及旧资产可用性。契约权威输入为[正式控制器和 DTO](../api/README.md)，通过原 WebAPIModel 导出链生成 OpenAPI，不手写另一份合同。
