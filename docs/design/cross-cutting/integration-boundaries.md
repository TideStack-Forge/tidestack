# Ouroboros 集成边界

## 目标

本页用于说明哪些边界属于平台内部协作，哪些属于对外集成或基础设施适配，帮助维护者在扩展系统时避免把外部系统约束直接揉进核心模块。

## 平台内边界

平台内边界首先体现在层次分工上：

- `core` 定义模型和执行内核。
- `security` 提供统一安全边界。
- `ability` 封装可复用运行时能力。
- `app-module`、`dev-module`、`platform`、`frontends` 负责具体交付。

像 `document-management` 这样的应用模块，应复用平台已有的数据、权限、UI、存储和配置能力，而不是在应用层重新造一套基础设施抽象。平台内边界一旦被打穿，后续模块会越来越难复用。

## 外部系统边界

外部系统接入应通过明确的适配边界完成，而不是让核心模型直接依赖外部平台协议：

- 外部认证或第三方身份源，应停留在安全提供者与认证接入边界。
- 外部通知渠道，应停留在通知能力的通道抽象与实现边界。
- 外部版本控制、对象存储或文件系统，应通过对应能力模块的抽象接口进入平台。

对维护者而言，判断标准很简单：如果替换掉某个外部系统会导致 `core` 模型定义变化，那通常说明边界放错了。

## 前后端边界

前后端边界由模型、接口和交付链共同定义：

- 后端通过 `ui-model`、`webapi-model` 等模型族定义页面元数据与 API 语义。
- `frontends/web` 负责前端基座、微前端模块和 SDK 的独立发布。
- `platform/*` 模块负责把后端能力暴露为运行入口，但不直接等于浏览器侧交付物。

因此，前后端边界不是“谁拥有页面代码”这么简单，而是“谁定义元数据、谁暴露接口、谁负责最终交付”的分层协作问题。

## 基础设施边界

数据库、缓存、文件系统、对象存储、镜像和部署目录都属于基础设施边界：

- `platform/ouroboros-develop`、`platform/ouroboros-mothership` 中的数据库驱动、Redis、Liquibase、上传存储路径、元数据路径和微前端部署路径，是运行时基础设施约束。
- `document-management` 的 `StorageService` 抽象说明文件内容存储不应和文档元数据仓储紧耦合。
- `frontends/web` 的基座镜像与 SDK 发布规则说明前端交付物同样有独立的基础设施边界。

基础设施可以被平台统一承接，但不应变成核心模型的内嵌假设。

## 演进约束

后续扩展时应坚持以下约束：

- 先定义适配边界，再接入外部系统，不要把外部协议直接泄漏到核心抽象。
- 先明确平台内层次边界，再决定新能力落在 `ability`、`app-module` 还是 `platform/frontends`。
- 当前后端或存储方式发生变化时，优先调整交付与适配层，而不是回写 `core` 模型本身。

只有这样，`docs/design` 才能持续表达“平台能力的稳定骨架”，而不是不断追着某个外部系统的实现细节改写架构。
