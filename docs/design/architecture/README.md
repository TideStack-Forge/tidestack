# 系统架构设计

本目录存放 Ouroboros 系统架构相关的设计文档。

## 架构概览

Ouroboros 采用分层架构，从底层到上层依次为：

```
platform (平台运行时)
    ↑
app-module / dev-module (应用层)
    ↑
ability (业务能力层)
    ↑
security (安全层)
    ↑
core (核心引擎层)
    ↑
libs (基础设施层)
```

## 架构原则

### 1. 分层依赖原则

**规则**: 依赖可指向允许的下层，禁止向上依赖；包族拆分和存量例外以现行架构约束及 ArchUnit 定义为准。

```
✓ 允许: ability → core → libs
✗ 禁止: core → ability
✓ 允许: ability → libs（使用公共底层合同）
```

**扩展**：core 定义 SPI、ability 提供实现时，源依赖仍指向 core；这不是允许 core 反向依赖 ability 的豁免。

### 2. 模块自治原则

每个模块应：
- 有清晰的职责边界
- 通过接口暴露能力
- 最小化对外部模块的依赖
- 提供完整的测试覆盖

### 3. 横切关注点原则

横切关注点（如安全、配置、可观测性）通过以下方式接入：
- SPI 扩展点
- Spring Boot 自动配置
- AOP 切面
- 事件总线

### 4. 演进式架构原则

架构应支持渐进式演进：
- 保持向后兼容
- 提供迁移路径
- 记录架构决策（ADR）
- 跟踪技术债

## 架构约束

### 强制约束（通过 ArchUnit 检查）

1. **分层依赖**: 严格遵守分层依赖规则
2. **循环依赖**: 禁止模块间循环依赖
3. **包命名**: 遵循 `com.ouroboros.{domain}.*` 规范
4. **SPI 注册**: 所有 SPI 实现必须在 `META-INF/services/` 注册

### 软约束（通过代码审查）

1. **接口隔离**: 接口应小而专注
2. **依赖注入**: 优先使用构造器注入
3. **配置外部化**: 避免硬编码配置
4. **异常处理**: 使用统一异常体系
