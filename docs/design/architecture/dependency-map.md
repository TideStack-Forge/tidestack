# Ouroboros 依赖关系地图

## 顶层模块分组

本页只保留依赖分析所需的最小分组，并按维护约束强调顺序：`libs` 与 `core` 组成基础与核心能力来源，`security` 位于其上的独立安全边界，`ability` 再向上封装通用业务能力，`app-module` 与 `dev-module` 负责组合这些能力，`platform` 处于最上层交付位置；`frontends` 作为前端交付侧，与上层应用装配关系最紧。更完整的仓库顶层目录处置与范围划分由 `system-overview.md` 负责。

## 依赖方向规则

依赖方向应保持自下而上单向流动，避免高层实现细节反向渗透到低层：

- `libs` 作为最底层公共支撑，应尽量不依赖更高层模块。
- `core` 建立在 `libs` 之上，提供核心引擎抽象，但不应反向依赖 `security` 以上的交付层模块。
- `security` 位于 `core` 之上，负责统一安全边界；它可以依赖 `libs` 与 `core`，但不应把上层业务装配逻辑带回安全层。
- `ability` 位于 `security` 之后，消费底层稳定抽象与安全能力，对上提供配置、通知、组织、运行时等通用服务；它不应反向依赖具体 `app-module`、`dev-module` 或 `platform` 场景。
- `app-module`、`dev-module` 负责组合下层能力形成具体应用与开发支撑能力，`platform` 进一步承载最终平台交付；这些上层单元应依赖下层稳定能力，而不是把自己的流程规则倒灌回公共层。

依赖方向的核心目标，是让公共抽象稳定、上层组合灵活、发布边界清晰。

## 分层边界与边界穿透风险

需要重点避免的边界穿透包括：

- 禁止在 `libs` 或 `core` 中引入特定平台应用、开发模块或前端交付物的业务假设，否则会把可复用内核变成场景耦合实现。
- 避免 `ability` 直接承担本应属于 `platform` 或 `app-module` 的页面编排、部署入口或产品定制逻辑，否则中间层会失去复用价值。
- 避免绕过统一边界，直接在上层模块中复制底层扩展机制、配置协议或安全规则，这会让维护者无法从单一位置理解系统约束。
- 当前仓库以多模块 Maven 聚合构建，边界穿透即使短期能工作，也会提高跨模块联调、版本演进和 subtree 同步成本。

因此，设计文档中的“依赖关系地图”重点不是罗列所有模块，而是声明哪些依赖方向被鼓励、哪些依赖会在演进中放大风险。

## 模块组织与构建关系

仓库目录、Maven 聚合和设计层级并不是一一同构关系：

- 仓库用顶层目录组织代码所有权和工程边界。
- Maven 根 `pom.xml` 通过 `bom`、`libs`、`ability`、`core`、`security`、`app-module`、`dev-module`、`platform`、`maven-archetypes` 聚合构建关系。
- 设计文档中的依赖地图只关心跨层依赖是否合理，不重复展开哪些目录属于正式模块群、哪些仅作为工程话题存在。

这意味着维护者在判断依赖时，需要同时看“设计层级是否允许”“模块组织是否合理”“构建关系是否会扩大耦合”，而不能只看某两个模块在 Maven 上能否声明依赖。
